## Claude Code Skills: The Passive Knowledge Layer That Enhances Your Workflow


_May 2026 · 14 min read · Skills · Global vs Local · Four Patterns · Real Templates_


After two weeks of utilizing Claude Code, I frequently encountered a persistent challenge: while Claude demonstrated intelligence, it lacked familiarity with _my_ workflows. It was unaware of the Test-Driven Development (TDD) process my team adheres to, our REST API conventions, or our specific error-handling practices. Each session required me to re-explain the same concepts.


This is precisely the problem that Skills are designed to address.


However, before I grasped the true nature of Skills, I held a fundamentally flawed mental model. If you are approaching this from CLAUDE.md, thinking that Skills are merely "additional instructions," you might be falling into the same trap I did. Let’s clarify that misconception.


## The Common Misunderstanding


Skills are **not** commands. They are **not** agents. They are not simply "smart prompts."


Skills are **passive knowledge modules**. Claude Code loads them based on context and references them automatically when relevant—without requiring any explicit invocation from you. They do not execute or run; they simply _know_ things, and Claude utilizes this knowledge when the situation calls for it.


Here’s a comprehensive breakdown of how these components differ:


| Component   | What It Is               | When It Activates                       |
| ----------- | ------------------------ | --------------------------------------- |
| **Skill**   | Passive knowledge module | Context-based — automatic               |
| **Agent**   | Specialized subassistant | Explicit delegation via Task tool       |
| **Command** | User-triggered action    | You type `/command-name`                |
| **Hook**    | Automation script        | Event-triggered (tool use, session end) |
| **Rule**    | Always-on guidelines     | Every message, every session            |


The key takeaway that changes everything: **a skill does not execute anything**. Agents are invoked to perform tasks, while agents _read skills_ to execute those tasks effectively. If you find yourself crafting a skill that "runs" something, you likely need a command or a script-backed skill with a corresponding executable—not a pure skill.

## Global vs Local: Understanding Skill Placement


Before creating any skills, determine their appropriate location. This decision influences visibility, loading behavior, and whether they are included with your project.


```vb
~/.claude/
└── skills/
    ├── my-global-skill/     ← 🌍 Available in ALL your projects
    │   └── SKILL.md
    └── learned/             ← Auto-generated by Claude (do not edit)
        └── ...
your-project/
└── .claude/
    └── skills/
        ├── api-design/      ← 👥 Project skill (commit to git, share with team)
        │   └── SKILL.md
        └── tdd-workflow/    ← 👥 Project skill
            └── SKILL.md
```


| Location                         | Scope             | Committed to Git?      | Best For                                            |
| -------------------------------- | ----------------- | ---------------------- | --------------------------------------------------- |
| `~/.claude/skills/`              | All your projects | No                     | Your personal workflows, coding philosophy          |
| `.claude/skills/` (project root) | This project only | Yes — shared with team | Team conventions, project-specific domain knowledge |
| `~/.claude/skills/learned/`      | All projects      | No                     | Auto-generated by Claude — do not edit manually     |


**Rule of thumb:** If it pertains to how _you_ work, it should be global. If it concerns how _this codebase_ operates, it should be a local project skill.


## Skill Structure


Each skill is a directory that must contain at least one required file:


```vb
.claude/skills/my-skill/
├── SKILL.md          ← required, must be non-empty
├── config.json       ← optional — configurable behavior
├── scripts/          ← optional — companion executables
│   └── run.js
└── references/       ← optional — sub-documents for complex schemas
    └── schema.md
```


### The Frontmatter


Every `SKILL.md` begins with YAML frontmatter:


```vb
---
name: api-design
description: REST and GraphQL API design conventions, HTTP status codes, pagination patterns
origin: user
---
```


**Three strict rules for frontmatter:**

1. The `name` must exactly match the directory name.
2. The `description` must be an **inline string** — not a literal block (`|` or `|-`). Literal blocks disrupt auto-activation matching.
3. The `origin` is `user` for your own skills and `community` for those ported from elsewhere.

### Required Sections


A well-structured skill should contain four sections, in the following order:


```vb
## When to Activate
(The most important section — more on this below)
## Core Reference
(The actual knowledge — tables, rules, conventions)
## Code Examples
(Copy-pasteable, not pseudocode)
## Anti-Patterns
(What NOT to do, with concrete examples)
```


**Length target:** 200–500 lines. Hard cap: 800 lines. A skill exceeding 800 lines is likely attempting to cover too much ground. Consider splitting it.


## The Importance of the "When to Activate" Section


This section is not merely documentation; it serves as the primary signal for Claude’s auto-discovery—determining whether to load this skill into context at all. A vague section can lead to inconsistent or missed activations.


**Bad Example:**


```vb
## When to Activate
When working on APIs.
```


**Good Example:**


```vb
## When to Activate
- Designing new REST or GraphQL API endpoints
- Reviewing an existing API contract for consistency
- Adding pagination, filtering, or sorting to a collection endpoint
- Writing OpenAPI/Swagger documentation
- Deciding between REST and GraphQL for a new service
- Implementing error response schemas
```


Specificity is crucial. Concrete scenarios provide Claude (and the runtime) with sufficient signals to match context accurately. Aim to write at least four specific, concrete scenarios; generic descriptions will not trigger activation.


## The Four Design Patterns


Through an analysis of the ECC (Everything Claude Code) project—comprising over 200 skills deployed to production—it has become clear that real skills fall into four distinct patterns. Understanding which one to use before you start can save you from unnecessary rewrites.


### Pattern A — Pure Reference


This consists of just a `SKILL.md`, which is dense, structured, and rich in tables and code snippets. It does not include scripts or sub-documents.


```vb
api-design/
└── SKILL.md   ← 524 lines of resource URL conventions,
                  HTTP status codes, pagination strategies,
                  and pre-deploy checklists
```


**Use when:** The knowledge is stable, requires no execution, and the reader needs an authoritative reference during tasks.


**Full example — api-design skill:**


````
---
name: api-design
description: REST API design conventions, HTTP status codes, pagination, and error response schemas
origin: user
---
## When to Activate
- Designing new REST endpoints
- Reviewing API contracts for consistency
- Adding pagination or filtering to collections
- Writing OpenAPI documentation
- Defining error response shapes
## Core Reference
### URL conventions
- Resources are plural nouns: `/users`, `/invoices`, not `/getUser`
- Nested resources for ownership: `/users/{id}/invoices`
- Actions that don't map to CRUD use verb phrases: `/invoices/{id}/send`
### HTTP status codes
| Code | Use case |
|------|----------|
| 200 | Successful GET, PATCH |
| 201 | Successful POST (resource created) |
| 204 | Successful DELETE (no body) |
| 400 | Malformed request / validation failure |
| 401 | Missing or invalid auth token |
| 403 | Valid token, insufficient permissions |
| 404 | Resource not found |
| 409 | Conflict (duplicate, state mismatch) |
| 422 | Semantically invalid (business logic rejection) |
| 429 | Rate limited |
| 500 | Internal server error — never leak details |
### Error response schema
```
{
  "error": {
"code": "INVOICE_ALREADY_SENT",
"message": "This invoice has already been sent.",
"field": "status"
  }
}
```
## Anti-Patterns
- ❌ Verbs in URLs: `/getInvoice`, `/createUser`
- ❌ Returning 200 for errors with `{ success: false }` in body
- ❌ Using 500 for client mistakes — that's a 4xx
- ❌ Different error shapes per endpoint
````

### Pattern B — Script-Backed

This pattern includes a `SKILL.md` that outlines a workflow, along with companion scripts that execute it.

```text
continuous-learning/
├── SKILL.md            ← defines the workflow
├── config.json         ← configurable thresholds
└── evaluate-session.sh ← does the actual work
```

The key design decision here is to use a `Stop` hook (which fires once at the end of a session), **not** a `UserPromptSubmit` hook (which fires with every message). The difference in overhead is significant—one execution versus one per message.

```text
---
name: continuous-learning
description: Evaluate each coding session and extract lessons for future improvement
origin: user
---
## When to Activate
- At the end of any coding session
- When a task takes significantly longer than expected
- After fixing a bug that required multiple correction cycles
- When a pattern appears that should be remembered
## Core Reference
This skill runs via a Stop hook — once at session end, not per-message.
### What to evaluate
1. Decisions made and why
2. Mistakes and how they were corrected
3. Patterns that worked well
4. Patterns to avoid next time
### Output format
Append to `~/.claude/skills/learned/session-log.md`:
- Date + project
- Key decisions
- Lessons extracted
- Rules to add to CLAUDE.md (if any)
```

**config.json:**

```json
{
  "min_session_duration_minutes": 10,
  "output_path": "~/.claude/skills/learned/session-log.md",
  "max_lessons_per_session": 5
}
```

**Use when:** The skill involves a concrete execution step—fetching data, writing files, or running analyses—but Claude still needs to understand the workflow to orchestrate it.

### Pattern C — Workflow

This pattern does not include scripts, but the `SKILL.md` is **prescriptive**, outlining sequential steps that Claude must follow—enforcing a process rather than merely providing a pattern.

```text
tdd-workflow/
└── SKILL.md   ← 514 lines enforcing:
                  write test → RED → implement → GREEN
                  → refactor → verify coverage
```

**Full example — tdd-workflow skill:**
```


## name: tdd-workflow
description: Test-driven development workflow with git checkpoints and coverage gates
origin: user


## When to Activate

- Implementing any new feature
- Fixing a bug (write regression test first)
- Refactoring existing code
- Adding a new API endpoint

## The Workflow


### Step 1 — Write the failing test


Write a test that describes the desired behavior.
Run it. Confirm it fails with the expected error (RED).
Never skip this step — a test that doesn't fail first isn't a test.


```plain text
pnpm test --watch src/feature.test.ts
# Must see: FAIL ✗ [your test name]
```text
### Step 2 — Implement the minimum
Write the minimum code to make the test pass.
No extra logic. No "while I'm here" changes. GREEN only.
### Step 3 — Git checkpoint
```


git add -p   # stage intentionally, not blindly
git commit -m "feat: [description] (green)"


```vb
### Step 4 — Refactor
Clean up the implementation. Remove duplication. Improve names.
Run tests after every change. Never refactor on a red test.
### Step 5 — Verify coverage
```


pnpm test:coverage


# Gate: no new lines below 80% branch coverage


```vb
## Mocking patterns for this project
- Supabase: use `createMockSupabaseClient()` from `src/test/mocks/supabase.ts`
- Redis: use `ioredis-mock` — never mock Redis manually
- OpenAI API: use `nock` to intercept HTTP, not jest.mock
## Anti-Patterns
- ❌ Writing implementation before the test
- ❌ Writing multiple tests before any implementation
- ❌ Committing on a red test (except the initial failing test commit)
- ❌ Skipping the refactor step — green doesn't mean done
```


**Use when:** You want to enforce a process rather than simply inform about one.


### Pattern D — Reference + Sub-Documents


This pattern features a concise `SKILL.md` that delegates extensive structural details to a `references/` subdirectory. The main file remains easily scannable while complex schemas are stored separately.


```vb
brand-voice/
├── SKILL.md                         ← 98 lines, remains scannable
└── references/
    └── voice-profile-schema.md      ← heavy schema, loaded on demand
```


```vb
---
name: brand-voice
description: Generate consistent brand voice profiles for content and documentation
origin: user
---
## When to Activate
- Writing customer-facing documentation
- Drafting marketing copy or product descriptions
- Reviewing content for tone consistency
- Onboarding a new content contributor
## Core Reference
Produce a VOICE PROFILE block that downstream skills can consume directly.
Use the schema defined in `references/voice-profile-schema.md`.
The three voice dimensions:
- **Clarity** — plain language, no jargon unless defined
- **Warmth** — human, not corporate; confident, not boastful
- **Precision** — specific claims, not vague reassurances
## Anti-Patterns
- ❌ Generic tone ("professional and friendly") without measurable signals
- ❌ Using passive voice in action-oriented contexts
- ❌ Different voice in docs vs in-product copy
```


**Use when:** The skill generates a reusable artifact—a schema, profile, or template—that other skills or commands can utilize.


## Developing Your First Three Skills


To achieve maximum return on investment with minimal complexity, follow this sequence:


### 1. Begin with a pure reference skill for your most frequently repeated explanation


Identify what you find yourself re-explaining to Claude most often. That will become your first skill.


```bash
mkdir -p .claude/skills/error-handling
touch .claude/skills/error-handling/SKILL.md
```


### 2. Create a workflow skill for your most critical process


Consider TDD, PR review, or deployment checklists—whatever your team prioritizes.


```bash
mkdir -p .claude/skills/pr-review
touch .claude/skills/pr-review/SKILL.md
```


### 3. Add a global personal skill that reflects your coding style


This skill should reside in `~/.claude/skills/` and apply universally:


```bash
mkdir -p ~/.claude/skills/my-coding-style
touch ~/.claude/skills/my-coding-style/SKILL.md
```


## Key Anti-Patterns to Avoid


From the ECC project's contributing guide and validation policy:


| Anti-Pattern                                      | Reason for Failure                                |
| ------------------------------------------------- | ------------------------------------------------- |
| Scope too broad ("Python, Django, and Flask")     | One skill = one domain                            |
| No code examples                                  | Theory without practice isn't actionable mid-task |
| Vague "When to Activate"                          | Auto-activation won't fire reliably               |
| Long prose instead of structured content          | Hard to scan when Claude is mid-task              |
| `description` as a literal block (`               | `)                                                |
| `name` doesn't match directory                    | Validator fails                                   |
| Script-backed skill using `UserPromptSubmit` hook | Runs every message — massive overhead             |
| Skill over 800 lines                              | Split it into two focused skills                  |


**One additional point to emphasize:** when adapting a skill from another project or tool, focus on copying the _idea_ — not the identity. Reshape it to fit your project’s context. A skill that requires knowledge of the upstream repository to understand its purpose risks confusing you later.


## The Checklist Before You Deploy a Skill


```vb
[ ] Focused on exactly one domain — not too broad
[ ] "When to Activate" has 4+ specific, concrete scenarios
[ ] At least one copy-pasteable code example (not pseudocode)
[ ] At least one Anti-Patterns section
[ ] Under 500 lines (800 hard cap — split if over)
[ ] Frontmatter: name matches directory, description is inline string
[ ] No sensitive data — no tokens, passwords, or absolute local paths
[ ] If script-backed: uses Stop hook, not UserPromptSubmit
[ ] If porting from another tool: renamed and reshaped to be native
[ ] Tested: trigger a session where the skill should activate and verify it does
```


## The Bigger Picture


Skills, CLAUDE.md, and SOUL.md function together as a layered system:


```vb
SOUL.md          ← How Claude communicates (tone, style)
CLAUDE.md        ← What Claude knows about you and your project
Skills           ← Domain knowledge Claude draws from mid-task
Commands         ← Workflows you trigger explicitly
Hooks            ← Automation that fires on events
```


CLAUDE.md serves as your permanent briefing. Skills represent the specialized knowledge base. Commands act as your shortcuts. These components are complementary rather than competitive.


The ECC project's summary succinctly encapsulates this philosophy:

> 
>
> _"Write skills you'd want to use yourself."_
>
>

If you wouldn’t reference the skill mid-task due to its vagueness, length, or breadth—neither will Claude.
