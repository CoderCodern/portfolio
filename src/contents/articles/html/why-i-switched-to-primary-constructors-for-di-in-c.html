Why I Switched to Primary Constructors for DI in C#

April 2026 6 min read C# · .NET · Backend

I resisted primary constructors for a while. When C# 12 extended them from record types to regular classes and structs, my first reaction was skepticism — an implicit mutable capture instead of explicit readonly fields felt like trading safety for convenience. After using them across several projects, I changed my mind. Here's what convinced me, and the one thing you actually need to watch out for.

what changed my mind

What Changed My Mind

Here's what my service classes used to look like:

csharp 
public class OrderService
{
    private readonly IOrderRepository _orderRepository;
    private readonly ILogger<OrderService> _logger;

    public OrderService(
        IOrderRepository orderRepository,
        ILogger<OrderService> logger)
    {
        _orderRepository = orderRepository;
        _logger = logger;
    }

    public async Task<Order?> GetOrderAsync(Guid id)
    {
        _logger.LogInformation("Fetching order {OrderId}", id);

        return await _orderRepository.GetByIdAsync(id);
    }
}

And here's what they look like now:

csharp 
public class OrderService(
    IOrderRepository orderRepository,
    ILogger<OrderService> logger)
{
    public async Task<Order?> GetOrderAsync(Guid id)
    {
        logger.LogInformation("Fetching order {OrderId}", id);

        return await orderRepository.GetByIdAsync(id);
    }
}

"The field declarations, the constructor body, the assignments. All gone. The parameters are captured and available throughout the class body."

That's the most common use case for primary constructors: dependency injection in service classes. You declare what you need, and use it directly. No intermediate ceremony.

di service classes

Where I Use Them Most: DI Service Classes

The place where primary constructors sold me is ASP.NET Core service classes. Here's a more realistic example from a checkout flow:

csharp 
public class CheckoutService(
    IPaymentProcessor paymentProcessor,
    IOrderRepository orderRepository,
    ILogger<CheckoutService> logger,
    IOptions<CheckoutOptions> options)
{
    public async Task<CheckoutResult> ProcessAsync(
        Cart cart,
        CancellationToken ct = default)
    {
        var settings = options.Value;

        if (cart.Total < settings.MinimumOrderAmount)
        {
            logger.LogWarning("Order below minimum: {Total}", cart.Total);
            return CheckoutResult.BelowMinimum;
        }

        var order = Order.Create(cart);

        await paymentProcessor.ChargeAsync(order, ct);
        await orderRepository.SaveAsync(order, ct);

        logger.LogInformation("Checkout complete for order {OrderId}", order.Id);

        return CheckoutResult.Success;
    }
}

Four dependencies, zero boilerplate. The class reads top-to-bottom without any noise.

Took me embarrassingly long to stop complaining about implicit captures and just use this.

This pattern works well because service classes typically don't need to validate or transform their dependencies. The DI container provides them, and you use them. Primary constructors are a perfect fit for this — they're designed for exactly this scenario.

entity construction

Entity Construction (With a Caveat)

Primary constructors also work for domain entities and value objects where you want to enforce required parameters at construction time:

csharp 
public class Order(Guid customerId, Money total)
{
    public Guid Id { get; } = Guid.NewGuid();
    public Guid CustomerId { get; } = customerId;
    public Money Total { get; } = total;
    public OrderStatus Status { get; private set; } = OrderStatus.Pending;
    public DateTime CreatedAt { get; } = DateTime.UtcNow;

    public void Confirm()
    {
        if (Status != OrderStatus.Pending)
        {
            throw new InvalidOperationException(
                $"Cannot confirm order in {Status} status.");
        }

        Status = OrderStatus.Confirmed;
    }
}

There's no way to create an Order without a customerId and total. The primary constructor makes this constraint visible right at the type declaration.

💡 Tip

Notice the key difference from the service class pattern: in entity classes, you assign primary constructor parameters to properties with initializers (= customerId). This makes the parameter's role explicit and the entity's shape immediately obvious. It also leads directly to the biggest pitfall.

the pitfall

The Pitfall That Almost Stopped Me

Here's why I held off for so long.

Primary constructor parameters are not readonly fields. When you use a parameter directly in the class body (like the service class pattern), the compiler captures it as a mutable variable. No readonly backing field is generated behind the scenes. This means you can accidentally reassign a parameter:

csharp 
public class OrderService(
    IOrderRepository orderRepository,
    ILogger<OrderService> logger)
{
    public async Task<Order?> GetOrderAsync(Guid id)
    {
        logger.LogInformation("Fetching order {OrderId}", id);

        return await orderRepository.GetByIdAsync(id);
    }

    public void SomeOtherMethod()
    {
        // This compiles. No warning. No error.
        orderRepository = null!;
        logger = null!;
    }
}
⚠️ Warning

That compiles without a warning. No error. Nothing. With a traditional constructor and private readonly fields, the compiler stops you immediately. With primary constructors, it stays completely silent.

If you need immutability guarantees, you can explicitly assign the parameter to a readonly field:

csharp 
public class OrderService(
    IOrderRepository orderRepository,
    ILogger<OrderService> logger)
{
    private readonly IOrderRepository _orderRepository = orderRepository;
    private readonly ILogger<OrderService> _logger = logger;

    public async Task<Order?> GetOrderAsync(Guid id)
    {
        _logger.LogInformation("Fetching order {OrderId}", id);

        return await _orderRepository.GetByIdAsync(id);
    }
}

But now you've lost most of the benefit. You're back to field declarations and assignments, just with a different syntax.

In practice, I've never hit this bug in a DI service class — you're unlikely to accidentally reassign logger in the middle of a method. But it can bite you in entity classes or value types where immutability actually matters. That's the one place where I stay cautious.

In five years of C# I have never accidentally reassigned _logger. The universe of bugs I'm protecting against here is very small.

traditional constructors

Where I Still Use Traditional Constructors

I haven't switched everything over. Here's when primary constructors aren't the right tool:

🚫 Primary Constructors Struggle Here
Complex validation before assignment
Multiple constructor overloads needed
5+ dependencies (your class is the problem)
✅ Primary Constructors Win
DI service classes — just declare and use
Entity construction enforcing required params
Any class where you use what you're given directly

Complex validation logic. If you need to validate parameters before assigning them, you need a constructor body. Primary constructors don't give you a place to run validation before the class body starts:

csharp 
public class EmailAddress
{
    private readonly string _value;

    public EmailAddress(string value)
    {
        if (string.IsNullOrWhiteSpace(value) || !value.Contains('@'))
        {
            throw new ArgumentException(
                "Invalid email address.", nameof(value));
        }

        _value = value;
    }
}

Multiple constructor overloads. Primary constructors support one signature. If you need overloads, you'll have to chain secondary constructors with this(...), which gets messy fast.

Too many parameters. Once you hit 5+ dependencies, the primary constructor line becomes hard to read. At that point, your class probably has too many responsibilities — and refactoring is the right answer, not formatting tricks.

summary

Summary

Here's what I've settled on after using primary constructors across several projects:

  • Use primary constructors for all DI service classes — the boilerplate savings are real
  • They work well for entity construction when you want required parameters at the type level
  • Parameters are captured as mutable variables, not readonly fields — know this
  • The mutable capture pitfall rarely bites in service classes; it matters more in entities
  • Stick with traditional constructors for validation-heavy types, multiple overloads, or bloated dependencies
✓ Verdict

The switch was worth it. Service classes are shorter, easier to scan, and the one pitfall is manageable once you know about it.

"You can outsource the boilerplate. You can't outsource understanding what the compiler is actually doing."
