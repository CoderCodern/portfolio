API Versioning Should Be Your Last Resort

May 2026 9 min read System Design · API Design · .NET

Previously, I discussed implementing API versioning in ASP.NET Core — but that's the wrong starting question. The right question is when to version an API, and the honest answer is: far less often than your instincts suggest.

Every API team arrives at the same reflex:

"Just create v2."

It feels responsible. What it actually produces is two APIs, two sets of documentation, two diverging behaviors — and a migration project clients will delay until the end of time. Versioning is a tool for compatibility, not a design strategy.

Most API changes don't require a new version — they require better change management. When you treat contract changes as a versioning problem, you duplicate APIs. When you treat them as a change management challenge, you start asking better questions:

  • Can I add instead of replace?
  • Can old and new behaviors coexist temporarily?
  • Can I introduce a new operation instead of altering an existing one?
  • Can I deprecate safely with telemetry and a migration path?

That last bullet is doing more work than it looks like. We'll get there.

what breaks clients

What Actually Breaks Clients?

Breaking changes aren't just about URLs. Clients experience breakage when you:

  • Remove or rename fields
  • Change the meaning of existing data
  • Tighten request validation
  • Modify pagination or error formats
  • Assume enum-like values are permanently closed

This single structural change silently destroys every client that ever integrated with your endpoint:

json 
// Before — every client expects a number
{ "total": 100 }

// After — field changed from number to object
{ "total": { "amount": 100, "currency": "USD" } }

No path changed. No endpoint renamed. Still broke every client parsing that field.

❌ The instinct
Should this be v2?
✅ The right question
Can old and new contracts coexist safely?

That reframe changes everything that follows.

compatibility rules

The Compatibility Rules

To make an API age gracefully, four rules cover most scenarios:

  • Maintain existing fields and behaviors
  • Never turn optional request data into required data
  • Never alter the functionality of an existing operation
  • Ensure anything new is additive and optional by default

These align with Z. Nemec's API Change Management principles: don't remove anything, don't change processing rules, don't make optional elements mandatory, and ensure additions are optional. Follow these consistently and most "versioning problems" revert to standard contract evolution.

✓ Verdict

The changes that don't fit these four rules? Those are the ones that actually warrant a version bump. Think of the rules as a filter: if you can satisfy all four, you don't need v2.

add, don't replace

1. Add, Don't Replace

The safest change is almost always an additive one. Suppose your original GET /orders/{id} response looks like this:

json 
{
  "id": "ord_123",
  "status": "paid",
  "total": 100
}

Instead of replacing total with a richer structure, introduce a new field alongside the existing one:

json 
{
  "id": "ord_123",
  "status": "paid",
  "total": 100,
  "totalMoney": {
    "amount": 100,
    "currency": "USD"
  }
}

Existing clients keep using total. New clients adopt totalMoney. Mark the old field deprecated, track its usage, and remove it only after a genuine migration window — not because you think no one is using it.

Yes, this means living with a slightly redundant contract for a while. That's the price of compatibility. A beautifully clean contract that breaks clients every six months isn't actually clean.

tolerant readers

2. Make Clients Tolerant Readers

A well-designed client shouldn't fail because the server added a field it doesn't recognize. If a response evolves from:

json 
{ "id": "ord_123", "status": "paid" }

To:

json 
{ "id": "ord_123", "status": "paid", "estimatedDeliveryDate": "2026-05-29" }

Older clients should ignore the new field and continue functioning. In .NET, System.Text.Json does this by default. The real challenge is teams that want backward compatibility while generating client models that reject any unexpected field in the response.

⚠️ Warning

Strict generated SDKs and contract tests that demand exact JSON matches are self-inflicted breaking changes. Your server is allowed to add optional data. Your clients need to be robust enough to ignore what they don't understand. If yours can't — fix the clients, not the API.

behavior contracts

3. Don't Change What an Existing Operation Does

Fields and shapes dominate compatibility discussions. The most dangerous breaking changes are behavioral. The URL is unchanged, the request body identical, the response structure the same — and the operation quietly does something different on the server.

Consider DELETE /orders/{id}, originally a soft delete: order transitions to archived, stays in the database, shows in audit reports, recoverable by support. The implicit contract clients integrated against:

  • The order is recoverable
  • Related invoices and shipments remain unaffected
  • Audit history is preserved
  • The call can be safely retried

The team decides soft deletes are too complicated and converts DELETE to a hard delete: row permanently removed, invoices cascaded or orphaned, audit history loses references, retry after a network interruption deletes the wrong record. The SDK call still compiles. The response still returns 204 No Content. A support tool that called DELETE and then "undid" it now silently destroys data.

If you need a hard delete, expose it as a new operation and leave the existing one intact:

text 
DELETE /orders/{id}             # soft-delete — unchanged
DELETE /orders/{id}?purge=true  # new, opt-in hard delete

Or introduce a proper resource: DELETE /orders/{id}/purge. Then the destructive path has its own name, its own permissions, and can't be accidentally triggered by someone calling a familiar endpoint.

⚠️ Warning

Once an operation is released, its behavior becomes part of the contract — whether or not it was explicitly documented. You can add new operations alongside it. You can deprecate it. You cannot silently change what it does.

validation changes

4. Be Very Careful With Validation

Two variations of the same mistake: changing an existing optional field to required, or introducing a brand-new mandatory field. Both break older clients the same way. Yesterday, this was a valid POST /orders body:

json 
{
  "customerId": "cus_123",
  "currency": "USD"
}

Today the API requires country for tax calculations:

json 
{
  "customerId": "cus_123",
  "currency": "USD",
  "country": "US"  // new required field — breaks every existing integration
}

Whether country was previously optional or nonexistent, every existing integration starts failing at runtime. Safer approaches:

  • Accept missing country and infer it from a billing profile during a transition period
  • Make it optional on the existing endpoint; introduce a new POST /checkout-sessions for the stricter model
  • Never ship a new field as required unless it's on a brand-new endpoint
💡 Tip

The rule covering both scenarios: anything added to the contract must be optional, and anything that was optional must remain optional. Response changes get careful design review. Validation changes deserve exactly the same treatment — they fail just as loudly at runtime.

new operations

A New Operation Is Often Cheaper Than a New Version

Sometimes a use case evolves enough that stacking flags and optional params on an existing endpoint becomes genuinely confusing:

text 
POST /orders?validateOnly=true&includeTaxEstimate=true&reserveInventory=true

That's not one operation — that's three workflows sharing a URL and a prayer.

❌ The reflex
Create v2/orders and drag the rest of the API with it
Every consumer re-evaluates their entire integration
✅ The better call
Introduce new operations that explicitly own the new behavior
Existing clients are completely unaffected
text 
POST /orders              # place an order — unchanged
POST /orders/quote        # cost estimate only
POST /checkout-sessions   # full guided flow with stricter model

POST /orders stays stable. New behavior gets a clear home. No existing client is dragged into a version migration they didn't ask for.

Generally much more efficient than creating /v2/orders and forcing every consumer to re-evaluate their entire integration. Most of them are busy. They will not migrate on your schedule.

proper deprecation

Deprecate Like You Mean It

Most deprecations are theater. Something gets documented somewhere, but nothing operationally changes. A real deprecation process has four elements:

  • Mark the old field or endpoint as deprecated in your OpenAPI description
  • Signal the deprecation at runtime via response headers
  • Provide consumers with a concrete migration path — not just a changelog note
  • Measure actual usage before removing anything

For HTTP APIs, runtime signaling is straightforward:

http 
Deprecation: true
Sunset: Wed, 31 Dec 2026 23:59:59 GMT
Link: <https://docs.example.com/migrations/orders-total>; rel="deprecation"

Visible in documentation. Apparent in live traffic. Linked to a migration guide that actually exists.

💡 Tip

Telemetry is not optional. If you don't know which clients still use a deprecated field, you're not managing change — you're guessing. Track by client ID, API key, or tenant. Wait until usage is genuinely near zero before removing anything. "I think no one uses this" is not a deprecation strategy.

when to version

When Versioning Is Actually The Right Call

None of this means versioning is wrong. Version when old and new semantics cannot safely coexist. Version when the resource model has fundamentally changed. Version when following the compatibility rules would produce a contract that's genuinely incomprehensible.

Deliberate versioning means choosing the smallest break you can justify: a new endpoint shape, a representation variant, or for public APIs, explicit URL versioning that's easy to communicate. The mechanism matters less than the reasoning behind it.

If you do version, pair it with a real deprecation process:

  • Mark old fields and endpoints as deprecated
  • Communicate a removal date — and commit to it
  • Provide migration examples, not just documentation
  • Monitor usage before removing anything
✓ Verdict

The hardest part of versioning isn't creating v2. It's getting clients to move off v1. Treat v1 as a long-term commitment the moment you ship it — because your clients already do, whether you meant them to or not.

takeaway

Takeaway

The best API version is often the one you never have to create. Before reaching for versioning, run through this checklist:

  • Can I add instead of replace?
  • Can old and new contracts coexist during a migration window?
  • Can I introduce a new operation instead of modifying an existing one?
  • Can I deprecate the old structure with docs, runtime headers, and telemetry?

Yes to any of these — you probably don't need a new version. No to all of them, and coexistence is genuinely not feasible — version deliberately, deprecate thoroughly, and give clients a real migration path.

Design contracts to evolve. Treat clients as long-term integrations. Reserve versioning for scenarios where compatibility actually runs out — not because it got a little inconvenient.

"The most effective API version is often the one you never have to create."
