Optimizing Bulk Database Updates in .NET: From Naive to Lightning-Fast

March 2026 10 min read .NET · PostgreSQL · Performance

Every outbox processor, job queue, and batch pipeline eventually hits the same wall: marking a set of rows as completed in bulk. I benchmarked seven different approaches against 1,000, 10,000, and 25,000 rows in PostgreSQL using Dapper and EF Core. For 10,000 rows, the slowest took 2,414ms. The fastest: 41ms. The bottleneck was rarely the SQL — it was the frequency of database interactions.

the setup

The Setup

Consider a table of orders, each requiring two updates: a change in status to "Processed" and a unique processed_at timestamp per row.

sql 
CREATE TABLE orders (
    id            UUID         NOT NULL PRIMARY KEY,
    customer_name TEXT         NOT NULL,
    status        TEXT         NOT NULL DEFAULT 'Pending',
    processed_at  TIMESTAMPTZ
);

The update payload is a simple record pairing each order ID with its timestamp:

csharp 
record OrderUpdate(Guid Id, DateTime ProcessedAt);

Ten lines of schema and a one-liner record — and the next 25 minutes of your architecture review will somehow be about how you update those rows at scale.

seven approaches

Seven Approaches, One Clear Winner

Approach 1: Naive Dapper — One UPDATE Per Row

The intuitive starting point: loop through the list and fire one UPDATE per row inside a transaction.

csharp 
await using var connection = new NpgsqlConnection(connectionString);
await connection.OpenAsync();
await using var transaction = await connection.BeginTransactionAsync();

foreach (var update in updates)
{
    await connection.ExecuteAsync(
        """
        UPDATE orders
        SET processed_at = @ProcessedAt,
            status       = 'Processed'
        WHERE id = @Id
        """,
        new { update.Id, update.ProcessedAt },
        transaction: transaction);
}

await transaction.CommitAsync();
⚠️ Warning

This is how every outbox processor starts. With 10,000 rows it makes 10,000 separate round-trips. Each ExecuteAsync sends SQL, waits for PostgreSQL to acknowledge, then moves on. Result: 2,414ms for 10k rows, over 6 seconds for 25k. Your database is fast. This code just refuses to let it prove that.

Approach 2: EF Core SaveChanges — Batched Round-Trips

EF Core batches generated SQL, grouping multiple statements into fewer round-trips. Setting MaxBatchSize high enough sends all 10,000 updates in a handful of network calls instead of thousands.

csharp 
var options = new DbContextOptionsBuilder&#x3C;AppDbContext>()
    .UseNpgsql(connectionString, o => o.MinBatchSize(5000).MaxBatchSize(10000))
    .Options;

await using var db = new AppDbContext(options);

var ids = updates.Select(u => u.Id).ToHashSet();
var orders = await db.Orders
    .Where(o => ids.Contains(o.Id))
    .ToListAsync();

var updateMap = updates.ToDictionary(u => u.Id);

foreach (var order in orders)
{
    order.Status = "Processed";
    order.ProcessedAt = updateMap[order.Id].ProcessedAt;
}

await db.SaveChangesAsync();
💡 Tip

EF Core's default batch size is 42. Raising MaxBatchSize to match your batch is the single biggest knob available if you're stuck with SaveChanges — but it still generates 10,000 individual UPDATE statements and requires an upfront SELECT to load the change tracker. You're reducing round-trips, not eliminating them.

Approach 3: Dapper + VALUES Table

Instead of N statements, construct one UPDATE that embeds all new values in a derived VALUES table. PostgreSQL receives a single statement, builds one execution plan, and updates every row in one pass.

sql 
UPDATE orders
SET processed_at = v.processed_at,
    status       = 'Processed'
FROM (VALUES
    (@Id0, @ProcessedAt0),
    (@Id1, @ProcessedAt1),
    ...
) AS v(id, processed_at)
WHERE orders.id = v.id::uuid

Here's the C# to build and execute that statement dynamically:

csharp 
await using var connection = new NpgsqlConnection(connectionString);
await connection.OpenAsync();
await using var transaction = await connection.BeginTransactionAsync();

const string updateTemplate =
    @"""
    UPDATE orders
    SET processed_at = v.processed_at,
        status       = 'Processed'
    FROM (VALUES
        {0}
    ) AS v(id, processed_at)
    WHERE orders.id = v.id::uuid
    """;

var paramNames = string.Join(
    ",\n    ",
    updates.Select((_, i) => $"(@Id{i}, @ProcessedAt{i})"));

var sql = string.Format(updateTemplate, paramNames);

var parameters = new DynamicParameters();
for (int i = 0; i &#x3C; updates.Count; i++)
{
    parameters.Add($"Id{i}", updates[i].Id.ToString());
    parameters.Add($"ProcessedAt{i}", updates[i].ProcessedAt);
}

await connection.ExecuteAsync(sql, parameters, transaction: transaction);

await transaction.CommitAsync();

The query text grows with the batch — 10,000 rows means 10,000 parameter pairs. Still well under PostgreSQL's 65,535-parameter hard limit for typical workloads, but worth knowing before you aim this at 100k rows. Approaches 6 and 7 sidestep this entirely.

Approach 4: EF Core ExecuteSqlRaw + VALUES

Same SQL as Approach 3, but executed through an EF Core DbContext. The advantage is sharing a transaction with other EF Core operations. Note that ExecuteSqlRawAsync requires NpgsqlParameter objects directly — Dapper's DynamicParameters won't work.

csharp 
await using var db = new AppDbContext(options);
await using var transaction = await db.Database.BeginTransactionAsync();

var paramEntries = new List&#x3C;NpgsqlParameter>();
var valueClauses = new List&#x3C;string>();

for (int i = 0; i &#x3C; updates.Count; i++)
{
    valueClauses.Add($"(@Id{i}::uuid, @ProcessedAt{i})");
    paramEntries.Add(new NpgsqlParameter($"Id{i}", updates[i].Id.ToString()));
    paramEntries.Add(new NpgsqlParameter($"ProcessedAt{i}", updates[i].ProcessedAt));
}

var sql = string.Format(updateTemplate, string.Join(",\n    ", valueClauses));

await db.Database.ExecuteSqlRawAsync(sql, paramEntries);

await transaction.CommitAsync();

Approach 5: Dapper CTE

A stylistic variation of Approach 3 using a named CTE instead of an inline derived table. One round-trip, same performance envelope — choose whichever syntax your team finds more readable in complex update logic.

sql 
WITH updates(id, processed_at) AS (
    VALUES
        (@Id0::uuid, @ProcessedAt0),
        (@Id1::uuid, @ProcessedAt1),
        ...
)
UPDATE orders
SET processed_at = updates.processed_at,
    status       = 'Processed'
FROM updates
WHERE orders.id = updates.id
csharp 
await using var connection = new NpgsqlConnection(connectionString);
await connection.OpenAsync();
await using var transaction = await connection.BeginTransactionAsync();

var valueClauses = string.Join(
    ",\n        ",
    updates.Select((_, i) => $"(@Id{i}::uuid, @ProcessedAt{i})"));

var sql =
    @$"""
    WITH updates(id, processed_at) AS (
        VALUES
            {valueClauses}
    )
    UPDATE orders
    SET processed_at = updates.processed_at,
        status       = 'Processed'
    FROM updates
    WHERE orders.id = updates.id
    """;

var parameters = new DynamicParameters();
for (int i = 0; i &#x3C; updates.Count; i++)
{
    parameters.Add($"Id{i}", updates[i].Id.ToString());
    parameters.Add($"ProcessedAt{i}", updates[i].ProcessedAt);
}

await connection.ExecuteAsync(sql, parameters, transaction: transaction);

await transaction.CommitAsync();

Approach 6: Dapper + UNNEST

Pass two typed arrays as parameters and let PostgreSQL expand them with UNNEST. No dynamic SQL, no growing parameter list, no format strings — the query text stays identical regardless of batch size.

csharp 
await using var connection = new NpgsqlConnection(connectionString);
await connection.OpenAsync();
await using var transaction = await connection.BeginTransactionAsync();

var ids = updates.Select(u => u.Id).ToArray();
var processedAts = updates.Select(u => u.ProcessedAt).ToArray();

await connection.ExecuteAsync(
    @"""
    UPDATE orders
    SET processed_at = v.processed_at,
        status       = 'Processed'
    FROM UNNEST(@Ids, @ProcessedAts) AS v(id, processed_at)
    WHERE orders.id = v.id
    """,
    new { Ids = ids, ProcessedAts = processedAts },
    transaction: transaction);

await transaction.CommitAsync();

"The query text is constant. The execution plan is cached. The arrays arrive in compact binary format. No matter whether you're updating 100 rows or 100,000, the SQL you send is exactly the same three lines."

Approach 7: Temp Table + Binary COPY

For extreme batch sizes, bypass SQL parameters entirely. Create a temp staging table, stream rows via Npgsql's binary COPY protocol (PostgreSQL's fastest data-load path), then execute a single UPDATE ... FROM.

csharp 
await using var connection = new NpgsqlConnection(connectionString);
await connection.OpenAsync();
await using var transaction = await connection.BeginTransactionAsync();

await connection.ExecuteAsync(
    @"""
    CREATE TEMP TABLE temp_updates (
        id           UUID        NOT NULL,
        processed_at TIMESTAMPTZ NOT NULL
    ) ON COMMIT DROP
    """,
    transaction: transaction);

await using (var writer = await connection.BeginBinaryImportAsync(
    "COPY temp_updates (id, processed_at) FROM STDIN (FORMAT BINARY)"))
{
    foreach (var u in updates)
    {
        await writer.StartRowAsync();
        await writer.WriteAsync(u.Id, NpgsqlTypes.NpgsqlDbType.Uuid);
        await writer.WriteAsync(u.ProcessedAt, NpgsqlTypes.NpgsqlDbType.TimestampTz);
    }
    await writer.CompleteAsync();
}

await connection.ExecuteAsync(
    @"""
    UPDATE orders
    SET processed_at = t.processed_at,
        status       = 'Processed'
    FROM temp_updates t
    WHERE orders.id = t.id
    """,
    transaction: transaction);

await transaction.CommitAsync();

The ON COMMIT DROP clause cleans up the staging table automatically at transaction end. Binary COPY transmits rows in PostgreSQL's native binary wire format — no parameter serialization, no SQL string overhead. At 10k rows it matches UNNEST at 41ms; the gap widens in favour of COPY at 100k+ rows where the temp-table overhead becomes negligible compared to the data volume.

✓ Verdict

The decisive jump is between Approach 2 and 3 — from 1,030ms to 89ms, a 10× improvement that comes entirely from eliminating round-trips, not from tuning SQL. Approaches 6 and 7 push further by removing dynamic SQL and parameter limits. For PostgreSQL, UNNEST is the pragmatic default. Reach for binary COPY when batch sizes exceed 100k and the temp-table setup overhead is worth the data-transmission savings.

summary

Summary

The takeaway is blunt: reducing round-trips is the only lever that meaningfully moves performance. Cutting 10,000 database calls down to one is where the gains live. Everything else is secondary.

  • EF Core SaveChanges is not a bulk-update tool — batching reduces round-trips but still generates N individual UPDATE statements and loads the change tracker via SELECT
  • For PostgreSQL, UNNEST is the pragmatic default — fixed query text, two parameters, stable execution plans, no parameter count ceiling
  • Binary COPY is for extreme scale — stream data in binary format, bypass the parameter system entirely, no SQL string expansion
  • Dapper and EF Core coexist — raw SQL bulk updates can share an EF Core transaction with change-tracked operations without conflict

"You don't need a faster database. You need fewer conversations with the one you already have."
