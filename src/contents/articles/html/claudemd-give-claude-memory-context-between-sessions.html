CLAUDE.md: Give Claude Memory & Context Between Sessions

May 2026 12 min read Claude Code · CLAUDE.md · Configuration

While Week 1 focused on getting Claude Code operational, Week 2 is about making it understand you. The single most impactful lever in the entire Claude Code ecosystem is a plain markdown file named CLAUDE.md. Master it, and every session begins with Claude already knowing your stack, your rules, and your working style. Neglect it, and you spend tokens reintroducing yourself every single day.

Here's what we'll cover: the full file hierarchy, what goes in each layer, the SOUL.md trick for giving Claude a personality, and the four rules from Karpathy's file that hit 220,000 combined GitHub stars.

understanding

Understanding CLAUDE.md

CLAUDE.md is a plain text file Claude reads before every session — before you type a single word. No schema, no validation, no required fields. Just markdown that shapes how Claude approaches your project.

Think of it as a briefing doc that runs automatically. Every session, Claude has already read it.

A config file that Claude actually reads, instead of silently ignoring. Novel concept in the AI tooling space.

"The problem it solves: Claude Code has no memory between sessions. Without CLAUDE.md, you start from scratch every time. With it, you start from everything that matters."

the hierarchy

The Hierarchy: Four Levels, One System

Here's what most people miss: CLAUDE.md isn't one file — it's a layered system. Claude reads from multiple locations and merges them all.

vb 
~/.claude/CLAUDE.md          ← 🌍 Global — YOUR soul, across all projects
~/.claude/SOUL.md            ← 🎭 Personality — how Claude communicates
~/projects/
└── my-app/
    ├── CLAUDE.md            ← 👥 Project — shared with team via git
    ├── CLAUDE.local.md      ← 🔒 Personal — your notes, gitignored
    └── src/
        └── api/
            └── CLAUDE.md    ← 📁 Subdirectory — lazy-loaded on demand
FileWho Sees ItWhen to Use It
~/.claude/CLAUDE.mdYou only, all projectsYour coding philosophy, style, personality
~/.claude/SOUL.mdYou only, all projectsCommunication style, tone, persona
./CLAUDE.mdWhole team (committed to git)Stack, commands, conventions, architecture
./CLAUDE.local.mdYou only (gitignored)Personal notes, WIP context, local paths
./src/api/CLAUDE.mdLoaded when Claude reads files thereDomain-specific rules for a module
💡 Tip

Precedence rule: more specific files win. If your global file says "use tabs" but the project file says "2-space indent," the project file wins. This means you can override global defaults per project without ever touching the global file.

global file

Level 1: The Global File — Your Developer DNA

~/.claude/CLAUDE.md loads in every project, every session. Put you here — not your codebase. Your coding philosophy, how you like Claude to respond, git preferences, tools you always reach for (e.g. pnpm over npm), and habits like always reviewing a /diff before big changes.

This is the file where "always use pnpm" gets to live rent-free across every project you will ever touch.

vb 
# Global Developer Config
## My Philosophy
- Prefer simple, readable code over clever abstractions
- Write the minimum code that actually solves the problem
- Readability beats brevity. Maintainability beats both.
## How I Work
- Always show me a `/diff` summary before large changes
- Ask before creating new files I didn't specifically request
- If you're uncertain about intent, ask — don't assume
## Git Style
- Conventional commits: feat:, fix:, chore:, docs:
- One logical change per commit
- Never use `--no-verify`
## Tools
- Package manager: pnpm (not npm or yarn)
- Always run typecheck after editing TypeScript files
soul.md

Level 2: SOUL.md — Infusing Claude with Personality

This concept reframed how I think about AI tools. Inspired by seaneoliver/claude-code-starter on GitHub, SOUL.md lives at ~/.claude/SOUL.md and focuses entirely on how Claude communicates — its tone, persona, and default behaviors when talking to you.

Why a separate file? Mixing personality and technical instructions creates noise. Keeping them separate keeps both effective.

❌ Without SOUL.md
Verbose when brevity would suffice
Asks clarifying questions before answering
Opens with "I'd be happy to help!"
Offers every possible cause instead of the most likely one
✅ With SOUL.md
Direct answer first, context only if needed
States interpretation, then proceeds
Starts with the code or command
Names the fix, then the trade-off
vb 
# Soul — Communication Style
## Persona
Direct, senior engineer. No preamble. No apologies. No "Great question!"
Start with the answer, then explain if needed.
## Response Defaults
- Lead with code or commands, not explanations
- Short responses unless complexity demands more
- No bullet points when prose would suffice
- Prefer "here's the fix" over "here are the possible causes"
## When I Ask for Something Ambiguous
- State your interpretation first, then proceed
- Avoid multiple clarifying questions — choose the most likely intent
- Present trade-offs, not just the solution
## Code Style in Responses
- Show diffs, not full file rewrites, for small changes
- Use the language/framework already in the file you're editing
- Match existing patterns in the codebase, don't introduce new ones
## What to Avoid
- Starting responses with "Certainly!", "Of course!", "Absolutely!"
- Restating my question back to me before answering
- Listing every possible option when I asked for a recommendation
✓ Verdict

The transformation is real. A bug-fix prompt shifts from a multi-paragraph exploration of possibilities to a targeted answer with working code. SOUL.md has arguably the highest ROI of any single file in the system.

project file

Level 3: The Project CLAUDE.md — Shared Team Knowledge

This is where most people start, and for good reason — it has the highest immediate return. Committed to git, it is visible to every teammate using Claude Code in your repo.

The golden rule: document what Claude gets wrong, not everything it should know. Claude can infer patterns from your codebase. CLAUDE.md is for the information it cannot infer.

The Optimal Structure

vb 
# [Project Name]
## What This Project Is
One or two sentences. Claude needs enough context to make architectural decisions.
## Stack
- Runtime: Node.js 20
- Framework: Express 5
- Database: PostgreSQL 15 with Prisma ORM
- Frontend: React 18 + Vite
- Testing: Vitest + Playwright
## Commands
- `pnpm dev`       — start local dev server (port 3000)
- `pnpm test`      — run unit tests
- `pnpm test:e2e`  — run Playwright tests
- `pnpm typecheck` — TypeScript check without emit
- `pnpm db:push`   — push Prisma schema changes
## Architecture
- @docs/ARCHITECTURE.md   ← read this before touching the auth module
- @docs/API-STANDARDS.md  ← REST conventions for all new routes
## Conventions
- camelCase for variables and functions
- PascalCase for React components and TypeScript types
- kebab-case for file names
- No default exports — named exports only
- Errors must be logged before they are thrown
## What Claude Often Gets Wrong Here
- Don't use `require()` — this is ESM only
- Don't add `console.log` for debugging — use the `logger` utility in src/utils/logger.ts
- Never modify migration files — create new ones instead
- The `auth` middleware must be applied before any route handler that touches user data
## When Compacting
Preserve: list of modified files, failing tests, current task description

The @filename Syntax — Your Secret Weapon

Instead of embedding lengthy documentation inline, reference it:

vb 
## Architecture
- @docs/ARCHITECTURE.md
- @docs/API-STANDARDS.md

Claude fetches these files on demand and integrates their content — without permanently inflating your token budget by embedding them at session startup.

⚠️ Warning

Don't inline @-file references directly inside CLAUDE.md body text — that embeds the entire referenced file on every session start. Write "For complex usage, see path/to/docs.md" instead. Claude fetches it only when relevant. The difference compounds across every session.

local file

Level 4: CLAUDE.local.md — Your Personal Layer

This file lives at your project root but is gitignored — invisible to your team. Use it for work-in-progress context, local path overrides, personal notes that would clutter the team file, and temporary rules during a feature branch.

Your local database runs on port 5433? Your team does not need to know. CLAUDE.local.md does.

vb 
# Local Notes (not committed)
## Current Focus
Migrating from REST to tRPC — auth routes are partially done.
Don't add new REST endpoints. All new APIs go through src/trpc/router.ts
## My Local Setup
- DB port: 5433 (non-standard)
- Redis: disabled locally, use in-memory mock
## WIP
- UserProfile component is being rewritten — don't reference the old one in src/components/UserProfileLegacy.tsx

The Karpathy Rules — 220,000 Stars for a Reason

In January 2026, Andrej Karpathy (OpenAI co-founder, former Tesla AI director) described the biggest shift in his programming workflow in two decades: going from 80% manual coding to 80% agent-driven coding with Claude Code. He identified four recurring failure patterns in LLM coding behavior.

Developer Forrest Chang distilled these observations into a single CLAUDE.md file — forrestchang/andrej-karpathy-skills — which accumulated 220,000 combined GitHub stars and held the top spot on GitHub Trending for 28 consecutive days. All from a 70-line markdown file.

vb 
## Think Before Coding
Don't assume. When a request is ambiguous, state your interpretation explicitly. Surface inconsistencies. Ask rather than guess. Present trade-offs before implementing. Don't manage confusion silently.
## Simplicity First
Write the minimum code that solves the stated problem. No unrequested abstractions, no speculative features, no "flexibility" nobody asked for. If the existing code is 100 lines, don't rewrite it to 1000 lines "for maintainability."
## Surgical Changes
Edit only what is directly relevant to the task. Don't touch adjacent code, comments, or formatting. Every changed line must trace directly to the request. Preserve style, naming, and patterns in the surrounding code.
## Goal-Driven Execution
Transform vague instructions into verifiable success criteria. "Fix the bug" becomes "write a test that reproduces it, then make it pass." Loop until the success criteria are met. Don't stop at "probably works."
✓ Verdict

Why did this go viral? Because every developer who had used an AI coding agent recognized these failure patterns immediately. And the fix was a text file anyone could copy in 30 seconds. That ratio is hard to beat.

To add Karpathy's rules to your own project:

bash 
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
optimization rules

The Optimization Rules — Lessons from the Community

After going through dozens of high-star repos and Anthropic's docs, here's what actually separates the files that work from the ones that quietly stopped working somewhere around line 200.

Keep It Under 300 Lines

LLMs reliably follow roughly 150–200 instructions. Claude Code's built-in system prompt already uses ~50 of those slots. So you have about 100–150 left. Past that, Claude doesn't start ignoring new instructions — it starts dropping all of them uniformly.

The test: for each line, ask — "Would removing this cause Claude to make a mistake?" If the answer is no, cut it.

Document What Claude Gets Wrong — Not Everything It Should Know

Claude can infer your coding patterns from the codebase. Don't document what it can infer. Focus on the surprises: the non-standard flag, the module where the pattern diverges, the decision that looks wrong but has a reason.

❌ Unnecessary (Claude infers this)
Use async/await for async operations
Handle errors with try/catch
Use descriptive variable names
✅ Necessary (Claude cannot know this)
Never use --legacy-peer-deps — it masks a conflict we are actively tracking
PaymentService is a singleton — never instantiate with new
The auth middleware must run before any route handler that touches user data
vb 
# ❌ Unnecessary (Claude infers this from the code)
- Use async/await for asynchronous operations
- Handle errors with try/catch
# ✅ Necessary (Claude can't know this)
- Never use the `--legacy-peer-deps` flag — it masks a real dependency conflict we're tracking
- The `PaymentService` class is a singleton — never instantiate it with `new`

Negative Constraints Need a Positive Alternative

An LLM told "never use X" can get stuck — it knows what not to do but not what to do instead. Always pair the prohibition with the preferred alternative.

vb 
# ❌ Claude gets stuck
- Never use --foo-bar flag
# ✅ Claude knows what to do
- Never use --foo-bar; prefer --baz instead (avoids the caching issue in CI)

Customize Compaction Behavior

Long sessions get compressed with /compact. Without explicit instructions, Claude may silently lose critical context during compaction.

vb 
## When Compacting
Always preserve: list of modified files, any failing tests, current task description, and any constraints established earlier in the session.

Use Hooks for Essential Actions — Not CLAUDE.md

Instructions in CLAUDE.md are advisory. Claude tries to follow them, but they can get overridden or forgotten in long sessions. If something must happen every time — run a linter, block secret commits — use a hook instead.

💡 Tip

Think of CLAUDE.md as a memo and hooks as an enforced policy. Memos get forgotten. Policies run regardless of what Claude decided it felt like doing that session.

bash 
## In CLAUDE.md (advisory)
- Run `pnpm typecheck` when you finish editing TypeScript files
## In Hooks (deterministic — always runs)
PostToolUse: bash -c "pnpm lint --fix $CLAUDE_TOOL_INPUT_FILE"

Quick Start: Generate Your First CLAUDE.md

Rather than writing it from scratch, let Claude generate the foundation for you.

bash 
# Inside your project folder
claude
> /init

The /init command analyzes your codebase — build systems, test frameworks, coding patterns — and generates a starter CLAUDE.md. Then run /memory to review what it already knows, and add only what is missing.

Add Karpathy's rules:

bash 
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md

Create your global files:

bash 
touch ~/.claude/CLAUDE.md   # Your developer DNA
touch ~/.claude/SOUL.md     # Your communication style
💡 Tip

The entire setup takes about 20 minutes. After that, every session opens with a Claude that already knows who you are, how you work, and what you value. That 20 minutes compounds across every session you will ever have.

treat like code

Treat CLAUDE.md Like Code

CLAUDE.md is a living document — most people set it once and forget it. When Claude repeats the same mistake, add a rule. When a rule goes stale, cut it. Run /memory after a few sessions to see what Claude figured out on its own, then update your file to match.

✓ Verdict

The best CLAUDE.md is not the most comprehensive one. It is the most accurate one. A 50-line file with no dead rules will outperform a 400-line manifest that Claude stopped reading somewhere around line 200.

"The best CLAUDE.md is not the most comprehensive one. It is the most accurate one."
