How to Securely Persist User Data in Zustand with Encrypted Storage

November 2024 6 min read Zustand · React · Security

When building applications, ensuring the security of sensitive user data is crucial. If you're using Zustand for state management and need to persist user data, you might worry about storing this data in plain text. This guide shows you how to combine Zustand's persist middleware with encryption to securely store data in the browser using localStorage.

why it matters

Why Secure Storage Matters

Browser localStorage is often used for client-side data persistence. However, data stored there is not encrypted — making it vulnerable to theft if a malicious actor gains access to the client device. By adding encryption, we ensure that even if data is accessed, it remains unreadable without the decryption key.

⚠️ Warning

localStorage is readable by any JavaScript running on the page — including third-party scripts. If you're storing authentication tokens, user details, or any PII there in plain text, you are one XSS away from a very bad day.

To be fair, your users probably aren't reading about the Web Cryptography API in their spare time. But the attackers are.

❌ Plain localStorage
Tokens and PII stored as readable JSON
One XSS vulnerability = full data exposure
No sign anything went wrong — until it did
✅ Encrypted Storage
Data stored as opaque ciphertext
Attackers get Base64 gibberish, not user records
Decrypt failures are caught silently — no crashes

In this guide we'll set up a secure storage mechanism using CryptoJS, integrate it with Zustand's persistence middleware, and protect sensitive user data like authentication details or personal preferences.

prerequisites

Prerequisites

To follow along you should have a basic understanding of Zustand and React, and Node.js installed in your development environment.

The usual suspects. If you don't have Node installed at this point, this might be the most exciting part of your day.

the setup

Setting Up Secure Storage

Let's create a secure storage implementation using CryptoJS — a battle-tested library for AES encryption in JavaScript.

Step 1: Install CryptoJS

Start by installing CryptoJS in your project:

bash 
npm install crypto-js

One package. No peer dependency conflicts. If you expected more ceremony here, I'm sorry to disappoint.

Step 2: Implement Secure Storage

Create a utility to encrypt and decrypt data before saving it to localStorage. This object implements the same interface Zustand's createJSONStorage expects:

ts 
import CryptoJS from 'crypto-js';

const CRYPTO_KEY = 'your-secure-encryption-key'; // Use an environment variable in production!

export const secureStorage = {
	getItem: (name: string): string | null => {
		const data = localStorage.getItem(name);
		if (!data) return null;
		try {
			const decrypted = CryptoJS.AES.decrypt(data, CRYPTO_KEY).toString(CryptoJS.enc.Utf8);
			return decrypted || null;
		} catch {
			return null;
		}
	},
	setItem: (name: string, value: string): void => {
		const encrypted = CryptoJS.AES.encrypt(value, CRYPTO_KEY).toString();
		localStorage.setItem(name, encrypted);
	},
	removeItem: (name: string): void => {
		localStorage.removeItem(name);
	}
};
💡 Tip

Never hardcode the encryption key as a string literal in production. Use an environment variable — import.meta.env.VITE_CRYPTO_KEY for Vite, or process.env.NEXT_PUBLIC_CRYPTO_KEY for Next.js. A leaked repository means a leaked key otherwise.

This utility ensures data is encrypted before being saved, decrypted when retrieved, and that invalid or corrupted data is safely ignored — no crashes, just a graceful null.

Step 3: Create a Persisted Zustand Store

Define a Zustand store for managing user state and persist it using the secure storage you just created:

ts 
import { create } from 'zustand';
import { persist, createJSONStorage } from 'zustand/middleware';
import { secureStorage } from '@/lib/secureStorage';

interface User {
	id: string;
	name: string;
	email: string;
}

interface UserState {
	user: User | null;
	setUser: (user: User | null) => void;
}

export const userStore = create<UserState>()(
	persist(
		(set) => ({
			user: null,
			setUser: (user) => set({ user })
		}),
		{
			name: 'user-state',
			storage: createJSONStorage(() => secureStorage)
		}
	)
);

Two things are doing the heavy lifting: persist middleware automatically saves and restores state across page reloads, and createJSONStorage wires your custom storage adapter in cleanly. The store's public API stays completely unchanged.

✓ Verdict

This pattern works for any sensitive state — auth tokens, user preferences, feature flags. Your components stay blissfully unaware of the encryption layer underneath.

Using the Store in Your App

You can now use userStore in your components to securely manage and persist user data:

ts 
import { userStore } from "@/stores/userStore";

export const UserProfile = () => {
  const { user, setUser } = userStore();

  const handleLogout = () => {
    setUser(null); // Clears user data
  };

  return (
    <div>
      <h1>Welcome, {user?.name || "Guest"}</h1>
      {user && <button onClick={handleLogout}>Logout</button>}
    </div>
  );
};

If you've ever accidentally logged a user object to the console and quietly panicked, this is the code that lets you relax. The localStorage entry is now ciphertext — your users' data is no longer one open DevTools tab away from exposure.

Testing Your Implementation

Before shipping, verify the full encrypt-decrypt cycle manually:

  • Add user data to the store by calling setUser with a test object
  • Open DevTools → Application → localStorage — confirm the value is an opaque encrypted string, not readable JSON
  • Refresh the page and verify the state is correctly restored from the encrypted entry

Conclusion

"Encryption doesn't make your app unbreakable — it just means attackers have to work harder than opening DevTools."

By combining Zustand with encrypted storage, we've built a secure and robust solution for persisting sensitive user data. The approach protects against data leaks while preserving Zustand's simple, flexible API. For production environments:

  • Use environment variables for the encryption key — never commit secrets to source control
  • Regularly rotate encryption keys for better long-term security
  • Consider key versioning so existing persisted data can still be decrypted during transitions
⚠️ Warning

This pattern encrypts data at rest in the browser, but it is not a substitute for proper backend authentication. The encryption key lives in your JavaScript bundle — a determined attacker can find it. Treat this as a defence-in-depth measure, not your primary security layer.
