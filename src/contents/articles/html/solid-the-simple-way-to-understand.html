SOLID: The Simple Way to Understand

February 2025 8 min read Architecture · TypeScript · Backend

SOLID principles are one of those things where everyone remembers the S, most people vaguely recall the O, and the rest starts to get fuzzy around the L. This article fixes that — each principle explained with TypeScript examples just realistic enough to be recognisable, and just painful enough to make the refactor feel satisfying.

"Everyone knows the S in SOLID. The other four are where the architecture actually happens."

Explaining these principles without code examples is how you get vague definitions that sound wise and mean nothing. So: TypeScript, concrete classes, real violations, real fixes. Let's go.

single responsibility

Single Responsibility Principle (SRP)

The easiest one to explain, and — somehow — one of the most commonly violated. The rule: a class should have one reason to change. Not two. Not five. One.

Here's a TaskManager class doing far too much with far too much confidence:

typescript 
class TaskManager {
  constructor() {}
  connectAPI(): void {}
  createTask(): void {
    console.log("Create Task");
  }
  updateTask(): void {
    console.log("Update Task");
  }
  removeTask(): void {
    console.log("Remove Task");
  }
  sendNotification(): void {
    console.log("Send Notification");
  }
  sendReport(): void {
    console.log("Send Report");
  }
}

This class connects to an API, manages tasks, sends notifications, and generates reports. It's not a TaskManager — it's a monolith in disguise, and it deserves everything that's about to happen to it in code review.

The sendNotification and sendReport methods don't belong here. If the notification service changes, why should the task management class change too? Split the responsibilities:

typescript 
class APIConnector {
  constructor() {}
  connectAPI(): void {}
}

class Report {
  constructor() {}
  sendReport(): void {
    console.log("Send Report");
  }
}

class Notificator {
  constructor() {}
  sendNotification(): void {
    console.log("Send Notification");
  }
}

class TaskManager {
  constructor() {}
  createTask(): void {
    console.log("Create Task");
  }
  updateTask(): void {
    console.log("Update Task");
  }
  removeTask(): void {
    console.log("Remove Task");
  }
}
💡 Tip

Single Responsibility Principle: each class must have one, and only one, reason to change. If you find yourself writing "and" when describing what a class does, it has too many responsibilities.

open closed

Open/Closed Principle (OCP)

Software entities should be open for extension but closed for modification. In practice: adding new behaviour shouldn't require editing existing code.

A useful smell to watch for — if a method has a long chain of if/else or switch statements based on a type field, you're probably violating OCP.

⚠️ Warning

Every time you add a new exam type to approveRequestExam, you open the existing method to bugs. The more types you add, the longer the method grows, the harder it is to test, and the higher the chance a new condition breaks an old one.

typescript 
type ExamType = {
  type: "BLOOD" | "XRay";
};

class ExamApprove {
  constructor() {}
  approveRequestExam(exam: ExamType): void {
    if (exam.type === "BLOOD") {
      if (this.verifyConditionsBlood(exam)) {
        console.log("Blood Exam Approved");
      }
    } else if (exam.type === "XRay") {
      if (this.verifyConditionsXRay(exam)) {
        console.log("XRay Exam Approved!");
      }
    }
  }

  verifyConditionsBlood(exam: ExamType): boolean {
    return true;
  }
  verifyConditionsXRay(exam: ExamType): boolean {
    return false;
  }
}

"What if we add ultrasound exams?" — you ask. The answer, with this code, is: find every if/else chain that mentions exam types and add another branch. Enjoy.

The fix: define an interface, implement it per type. Adding a new exam type means writing a new class — existing code stays untouched:

typescript 
type ExamType = {
  type: "BLOOD" | "XRay";
};

interface ExamApprove {
  approveRequestExam(exam: NewExamType): void;
  verifyConditionExam(exam: NewExamType): boolean;
}

class BloodExamApprove implements ExamApprove {
  approveRequestExam(exam: ExamApprove): void {
    if (this.verifyConditionExam(exam)) {
      console.log("Blood Exam Approved");
    }
  }
  verifyConditionExam(exam: ExamApprove): boolean {
    return true;
  }
}

class RayXExamApprove implements ExamApprove {
  approveRequestExam(exam: ExamApprove): void {
    if (this.verifyConditionExam(exam)) {
      console.log("RayX Exam Approved");
    }
  }
  verifyConditionExam(exam: NewExamType): boolean {
    return true;
  }
}
💡 Tip

Open/Closed Principle: software entities must be open for extension but closed for modification. When a new requirement means editing existing logic rather than adding new code, OCP is being violated.

liskov substitution

Liskov Substitution Principle (LSP)

The one with the intimidating name and the intuitive idea. If you have a base class and a subclass, you should be able to use the subclass anywhere the base class is expected — without anything breaking, and without any empty method implementations to paper over the gaps.

Here's a violation hiding in an inheritance chain:

typescript 
class Student {
  constructor(public name: string) {}

  study(): void {
    console.log(`${this.name} is studying`);
  }

  deliverTCC() {
    /** Problem: Postgraduate students don't deliver TCC */
  }
}

class PostgraduateStudent extends Student {
  study(): void {
    console.log(`${this.name} is studying and researching`);
  }
}

PostgraduateStudent extends Student, but postgraduate students don't deliver a TCC. The method exists on the parent, so it exists on the child — even though it shouldn't. The inheritance is lying about the relationship.

❌ Forcing inheritance
PostgraduateStudent extends Student
deliverTCC() exists on subclass — but does nothing
Every consumer of Student now gets a useless method
✅ Model the actual relationship
Student is the shared base
StudentGraduation adds deliverTCC()
StudentPostGraduation stays clean — no phantom methods
typescript 
class Student {
  constructor(public name: string) {}

  study(): void {
    console.log(`${this.name} is studying`);
  }
}

class StudentGraduation extends Student {
  study(): void {
    console.log(`${this.name} is studying`);
  }

  deliverTCC() {}
}

class StudentPostGraduation extends Student {
  study(): void {
    console.log(`${this.name} is studying and researching`);
  }
}
✓ Verdict

Liskov Substitution Principle: derived classes must be substitutable for their base classes. If a subclass needs to leave a method empty or throw "not implemented", the inheritance hierarchy is wrong — not the method.

interface segregation

Interface Segregation Principle (ISP)

A class should not be forced to implement interfaces and methods it doesn't use. The problem usually starts with a fat interface that tries to describe too many things at once:

typescript 
interface Employee {
  salary(): number;
  generateCommission(): void;
}

class Seller implements Employee {
  salary(): number {
    return 1000;
  }
  generateCommission(): void {
    console.log("Generating Commission");
  }
}

class Receptionist implements Employee {
  salary(): number {
    return 1000;
  }
  generateCommission(): void {
    /** Problem: Receptionist doesn't have a commission */
  }
}

generateCommission(): void { /* Receptionist doesn't have a commission */ } — an empty method implementation is not a solution. It's a comment written in TypeScript telling you the interface is wrong.

The fix is to split the interface by responsibility. Employee covers what all employees share. Commissionable covers what only some employees need:

typescript 
interface Employee {
  salary(): number;
}

interface Commissionable {
  generateCommission(): void;
}

class Seller implements Employee, Commissionable {
  salary(): number {
    return 1000;
  }

  generateCommission(): void {
    console.log("Generating Commission");
  }
}

class Receptionist implements Employee {
  salary(): number {
    return 1000;
  }
}
💡 Tip

Interface Segregation Principle: a class should not be forced to implement interfaces and methods it will not use. When a class implements an interface and leaves methods empty, the interface is doing too much — split it.

dependency inversion

Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules. Both should depend on abstractions. In practice: stop calling new inside your classes — inject the dependency instead.

Here's the tight-coupling version. OrderService constructs its own OrderRepository, which means swapping the repository for a test double — or a MongoDB implementation — means editing OrderService:

typescript 
interface Order {
  id: number;
  name: string;
}

class OrderRepository {
  constructor() {}
  saveOrder(order: Order) {}
}

class OrderService {
  private orderRepository: OrderRepository;

  constructor() {
    this.orderRepository = new OrderRepository();
  }

  processOrder(order: Order) {
    this.orderRepository.saveOrder(order);
  }
}
⚠️ Warning

When a class calls new ConcreteImplementation() in its constructor, it's taking ownership of that dependency. You can't swap it without changing the class. You can't test it without the real thing. You've just hidden a hardcoded dependency inside an object.

The fix: inject the dependency through the constructor. OrderService now depends on the type, not the implementation — meaning any repository that satisfies the type works:

typescript 
interface Order {
  id: number;
  name: string;
}

class OrderRepository {
  constructor() {}
  saveOrder(order: Order) {}
}

class OrderService {
  private orderRepository: OrderRepository;

  constructor(repository: OrderRepository) {
    this.orderRepository = repository;
  }

  processOrder(order: Order) {
    this.orderRepository.saveOrder(order);
  }
}
✓ Verdict

Dependency Inversion Principle: depend on abstractions, not concrete implementations. This is why dependency injection frameworks exist — not to be clever, but to make this principle the default rather than the exception.
