Implementing the Inbox Pattern for Reliable Message Consumption

April 2026 10 min read System Design · .NET · PostgreSQL

The Outbox pattern handles reliable publishing — but what about the consumer side? When a broker redelivers a message after a crash or timeout, your consumer can silently execute the same logic twice. The Inbox pattern is the consumer-side counterpart: it guarantees each incoming message is processed exactly once, even under relentless broker retries.

why you need it

Why You Need an Inbox

Most message brokers operate on an at-least-once delivery model. The broker guarantees every message will be delivered — but it does not guarantee each message arrives only once.

⚠️ Warning

At-least-once delivery is the default for RabbitMQ, Azure Service Bus, Kafka, and most other brokers. If your consumers aren't idempotent and you haven't centralized deduplication, you are already processing duplicates — you just haven't noticed yet.

Consider the common failure scenario:

  1. The broker delivers a message to your consumer.
  2. Your consumer processes the message successfully.
  3. Before the ACK reaches the broker, the connection drops.
  4. The broker assumes the message was lost and redelivers it.
  5. Your consumer processes the same message twice.

Step 5 is the one that shows up in your on-call rotation at 2 AM — usually after a deploy, usually on the message that charges a customer.

One solution is making each handler idempotent, but this requires every consumer to check a deduplication table before executing any work. The Inbox pattern centralizes that check in a single infrastructure mechanism. The process:

  1. A message arrives from the broker.
  2. Instead of processing immediately, write it to an inbox table.
  3. If the message already exists (duplicate), the write is silently ignored.
  4. A background process reads unprocessed messages and dispatches them.
the schema

Inbox Database Schema

The inbox_messages table stores every incoming message. Its structure deliberately mirrors the Outbox pattern's table:

sql 
CREATE TABLE IF NOT EXISTS inbox_messages (
    id UUID PRIMARY KEY,
    type VARCHAR(255) NOT NULL,
    content JSONB NOT NULL,
    received_on_utc TIMESTAMP WITH TIME ZONE NOT NULL,
    processed_on_utc TIMESTAMP WITH TIME ZONE NULL,
    error TEXT NULL
);

CREATE INDEX IF NOT EXISTS idx_inbox_messages_unprocessed
ON public.inbox_messages (received_on_utc, processed_on_utc)
INCLUDE (id, type, content)
WHERE processed_on_utc IS NULL;

Two design decisions carry most of the weight. The id column enables idempotent inserts via ON CONFLICT DO NOTHING — the entire deduplication mechanism reduces to a single SQL clause. The filtered index (WHERE processed_on_utc IS NULL) keeps the index lean by excluding processed rows; without it, you'd be scanning an ever-growing index for a shrinking working set.

💡 Tip

The INCLUDE (id, type, content) on the filtered index means the processor can satisfy queries entirely from the index without a heap fetch — a meaningful throughput gain once your inbox sees serious volume.

Messages between services share an IntegrationEvent base record. The MessageId is what drives deduplication at the id column:

csharp 
public abstract record IntegrationEvent(Guid MessageId);

public sealed record OrderCreatedIntegrationEvent(Guid OrderId)
    : IntegrationEvent(Guid.CreateVersion7());

Guid.CreateVersion7() generates time-ordered UUIDs — better index locality than random v4 GUIDs, available since .NET 9. Small detail, measurable difference at scale.

the consumer

Inbox Consumer

The consumer is a generic MassTransit IConsumer<T>. Its entire responsibility is to write the incoming message to the inbox table and return. No business logic. No event dispatching. No decisions.

csharp 
internal sealed class InboxConsumer<T>(NpgsqlDataSource dataSource)
    : IConsumer<T> where T : IntegrationEvent
{
    public async Task Consume(ConsumeContext<T> context)
    {
        await using var connection = await dataSource.OpenConnectionAsync(
            context.CancellationToken);

        const string sql =
            @"""
            INSERT INTO public.inbox_messages (id, type, content, received_on_utc)
            VALUES (@Id, @Type, @Content::jsonb, @ReceivedOnUtc)
            ON CONFLICT (id) DO NOTHING;
            """;

        await connection.ExecuteAsync(sql, new
        {
            Id = context.Message.MessageId,
            Type = typeof(T).FullName,
            Content = JsonSerializer.Serialize(context.Message),
            ReceivedOnUtc = DateTime.UtcNow
        });
    }
}

The ON CONFLICT (id) DO NOTHING clause is the critical line. If the broker redelivers the same message — after a crash, a timeout, or a network blip — the second insert is silently discarded. The consumer ACKs and moves on.

✓ Verdict

One generic InboxConsumer<T> covers every integration event type. Register it once, and every event gets the same idempotent persistence guarantee with zero per-handler boilerplate.

the processor

Inbox Processor

The processor runs as a background service or scheduled job. It fetches unprocessed messages in batches, dispatches them to their handlers, and writes the results — all within a single transaction:

csharp 
internal sealed class InboxProcessor(
    NpgsqlDataSource dataSource,
    IEventDispatcher eventDispatcher,
    ILogger<InboxProcessor> logger)
{
    private const int BatchSize = 1000;

    public async Task<int> Execute(CancellationToken cancellationToken = default)
    {
        await using var connection =
            await dataSource.OpenConnectionAsync(cancellationToken);
        await using var transaction =
            await connection.BeginTransactionAsync(cancellationToken);

        var messages = (await connection.QueryAsync<InboxMessage>(
            @"""
            SELECT id AS Id, type AS Type, content AS Content
            FROM inbox_messages
            WHERE processed_on_utc IS NULL
            ORDER BY received_on_utc
            LIMIT @BatchSize
            FOR UPDATE SKIP LOCKED
            """,
            new { BatchSize },
            transaction: transaction)).AsList();

        var processedAt = DateTime.UtcNow;
        var results = new List<(Guid Id, DateTime ProcessedAt, string? Error)>(
            messages.Count);

        foreach (var message in messages)
        {
            try
            {
                var messageType = Type.GetType(message.Type)!;
                var deserialized = JsonSerializer.Deserialize(
                    message.Content, messageType)!;

                await eventDispatcher.DispatchAsync(deserialized, cancellationToken);

                results.Add((message.Id, processedAt, null));
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Failed to process inbox message {Id}", message.Id);
                results.Add((message.Id, processedAt, ex.ToString()));
            }
        }

        if (results.Count > 0)
        {
            await connection.ExecuteAsync(
                @"""
                UPDATE inbox_messages
                SET processed_on_utc = v.processed_on_utc,
                    error = v.error
                FROM UNNEST(@Ids, @ProcessedAts, @Errors)
                    AS v(id, processed_on_utc, error)
                WHERE inbox_messages.id = v.id
                """,
                new
                {
                    Ids = results.Select(r => r.Id).ToArray(),
                    ProcessedAts = results.Select(r => r.ProcessedAt).ToArray(),
                    Errors = results.Select(r => r.Error).ToArray()
                },
                transaction: transaction);
        }

        await transaction.CommitAsync(cancellationToken);

        return messages.Count;
    }
}

Three implementation choices here are worth calling out explicitly:

  • FOR UPDATE SKIP LOCKED — multiple processor instances can run concurrently. Each instance locks the rows it selects; others skip them and take the next available batch. Horizontal scaling with no coordination overhead.
  • UNNEST batch update — all results written back in one round-trip instead of N individual UPDATEs. At batch size 1000, the difference between one query and a thousand is not subtle.
  • Error isolation — a failed message records its exception and doesn't block the rest of the batch. The transaction rolls back only if the entire batch operation fails, not on individual handler errors.

If the processor crashes mid-batch, the transaction rolls back and messages reappear in the next run as if nothing happened. This is where you appreciate PostgreSQL's transactional guarantees instead of taking them for granted.

watch out for

Things to Watch Out For

Table Growth

The inbox table grows indefinitely without cleanup. Delete processed messages after a retention period, partition by time range and drop old partitions, or archive to cold storage if you need the history. Pick one and implement it before production.

💡 Tip

A scheduled job running DELETE FROM inbox_messages WHERE processed_on_utc < NOW() - INTERVAL '7 days' is often all you need. The filtered index keeps live-message queries fast regardless of how many processed rows accumulate.

Poison Messages

If a message continually fails, it gets marked with an error each run but never leaves the active queue. Implement a maximum retry count — after N failures, move the message to a dead-letter table and trigger an alert.

⚠️ Warning

A poison message with no retry cap will silently consume processor cycles on every run, forever. It won't crash anything. It won't alert anyone. It will just quietly waste resources until someone looks at the error column and finds a timestamp from six weeks ago.

Ordering

ORDER BY received_on_utc gives approximate ordering by arrival time, but strict ordering is not guaranteed with SKIP LOCKED across multiple processors. If per-aggregate ordering matters, partition by aggregate ID and ensure only one processor handles each partition.

Monitoring

Track the lag between received_on_utc and processed_on_utc. A widening gap signals the processor can't keep up — increase batch size, tighten the polling interval, or scale out additional instances.

"We should add monitoring" is the distributed systems equivalent of "we should back up the database." Everyone agrees. Nobody does it until something goes wrong.

inbox vs idempotent

Inbox vs. Idempotent Consumer

Both patterns prevent duplicate processing, but they differ in when processing occurs and who controls retries.

The Idempotent Consumer processes inline: check dedup table → do the work → record dedup entry, all in one transaction. If it fails, the broker redelivers on its own schedule — you have no control over timing or backoff.

The Inbox pattern separates reception from processing. The consumer writes and ACKs immediately. The processor owns retries: reset processed_on_utc to NULL for messages under a retry threshold, implement backoff, scale horizontally.

⚠️ Idempotent Consumer
Processes messages inline — broker controls retry timing
Every handler must implement its own deduplication check
No batching — one message processed per broker delivery
✅ Inbox Pattern
Decouples reception from processing — you own retry scheduling
Single infrastructure layer centralizes all deduplication
Batch processing with SKIP LOCKED for horizontal scale

"The Inbox pattern doesn't make message processing simpler — it makes the complexity manageable. You trade implicit broker behaviour for explicit control you can observe, tune, and scale."

summary

Summary

The Inbox pattern is the consumer-side counterpart to the Outbox. Four mechanisms carry the implementation:

  • ON CONFLICT DO NOTHING — idempotent inserts; deduplication in a single SQL clause
  • Decoupled reception and processing — the consumer is a lightweight writer; all retry logic lives in the processor
  • FOR UPDATE SKIP LOCKED — horizontal scaling of the processor with no inter-instance coordination
  • UNNEST batch updates — all results written back in one database round-trip
