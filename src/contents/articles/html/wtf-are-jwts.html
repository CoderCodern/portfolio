WTF Are JWTs? The Self-Contained Tokens Behind Modern Auth

February 2025 8 min read Backend · Security · Auth

Every time you hit a protected API endpoint, a JWT is doing the heavy lifting — carrying your identity, roles, and session data in a single compact string that anyone can read but nobody can fake. Your auth provider generates them. Your database verifies them. Here's what's actually happening inside those three dots.

the history

The History of the JWT

Before JWTs, session-based authentication was the norm. The server created a session ID, stored it in a database, and sent it to the client as a cookie. Every authentication request needed a database lookup. Scaling that across multiple servers meant sharing session state — a headache that grew worse with every new service you added.

The rise of mobile apps, SPAs, and distributed systems made the problem acute. Developers needed something that worked across domains and platforms without constant database hits.

"a compact, URL-safe means of representing claims to be transferred between two parties."

That's RFC 7519, published by the IETF in May 2015. The whole idea: put all the user information directly in the token, sign it cryptographically to ensure authenticity. No database hit on every request. No shared session store. All the necessary information travels with the request itself.

  • Stateless auth — no server-side session storage needed
  • Cross-domain — works across different origins and services
  • Less DB load — verify with a public key, not a table lookup
  • Portable — carries any JSON-serializable data

"Stateless authentication" sounds like marketing until the fourth time you've debugged a session store sync issue at 2am.

the structure

The Structure of a JWT

A JWT is three base64url-encoded segments joined by dots: header.payload.signature. Paste one into jwt.io and you'll see them split apart. Here's what each segment actually contains.

The Header

json 
{
  "alg": "HS256",    // the algorithm used for signing
  "typ": "JWT"       // specifies this is a JWT
}

Two fields. alg says which algorithm signed the token; typ confirms it's a JWT. That's the entire header — metadata, not content. Don't expect more from it.

The entire header is two keys. JSON has seen worse.

The Payload

The payload carries the actual data — also called "claims." Some are standard, defined by RFC 7519 and included automatically by your auth provider:

json 
{
  // Default claims, included automatically by the auth provider
  "azp": "http://localhost:3000",   // Authorized party - client that requested the token
  "exp": 1639398300,             // Expiration time - timestamp the token becomes invalid
  "iat": 1639398272,                  // Issued at - timestamp when the token was created
  "iss": "https://clean-mayfly-62.clerk.accounts.dev", // Issuer created/signed the token
  "nbf": 1639398220,                  // Not before - timestamp before which token should not be accepted
  "sid": "sess_2ehYpzsasKNOZrpqPZ9yDWhrYVe",  // Session ID - unique identifier for this session
  "sub": "user_1deJLArSTiWiF1YdsEWysnhJLLY"   // Subject - unique identifier for the user
...

These standard claims handle token lifecycle (exp, iat, nbf), identity (sub, sid), and source (iss, azp). Then you layer in custom claims specific to your application:

json 
...
  "user_id": "user_abcdef123456789",
  "avatar": "https://example.com/avatar.jpg",
  "full_name": "Doe Maria",
  "email": "maria@example.com",
}

Put them together and you get the full payload:

json 
{
  "azp": "http://localhost:3000",
  "exp": 1639398300,             
  "iat": 1639398272,                  
  "iss": "https://clean-mayfly-62.clerk.accounts.dev", 
  "nbf": 1639398220,                  
  "sid": "sess_2ehYpzsasKNOZrpqPZ9yDWhrYVe",  
  "sub": "user_1deJLArSTiWiF1YdsEWysnhJLLY"
  "user_id": "user_abcdef123456789",
  "avatar": "https://example.com/avatar.jpg",
  "full_name": "Doe Maria",
  "email": "maria@example.com",
}
💡 Tip

Claims are base64-encoded, not encrypted. Anyone who intercepts the token can decode and read the payload. Only store non-sensitive identifiers here — look up sensitive data from your database using the sub claim.

The Signature

The signature is what makes JWTs trustworthy. Take the encoded header, add a dot, add the encoded payload, run it through HMAC-SHA256 (or whichever algorithm the header specifies) with a secret key:

javascript 
HMACSHA256(
  base64UrlEncode(header) + "." + 
  base64UrlEncode(payload),
  secret
)

Here's a working Node.js implementation that builds a JWT from scratch:

javascript 
function base64UrlEncode(str) {
 // Convert string to base64 and make URL safe
 return Buffer.from(str)
   .toString('base64')
   .replace(/\+/g, '-')
   .replace(/\//g, '_')
   .replace(/=/g, '');
}

function createJWT(header, payload, secret) {
 // Convert header and payload to strings
 const headerStr = JSON.stringify(header);
 const payloadStr = JSON.stringify(payload);

 // Base64Url encode header and payload
 const encodedHeader = base64UrlEncode(headerStr);
 const encodedPayload = base64UrlEncode(payloadStr);

 // Create signature input
 const signatureInput = encodedHeader + '.' + encodedPayload;

 // Create HMAC SHA256 signature
 const crypto = require('crypto');
 const signature = crypto
   .createHmac('sha256', secret)
   .update(signatureInput)
   .digest('base64')
   .replace(/\+/g, '-')
   .replace(/\//g, '_')
   .replace(/=/g, '');

 // Combine all parts
 return `${encodedHeader}.${encodedPayload}.${signature}`;
}

// Example usage:

 "alg": "HS256",
 "typ": "JWT"
};

 "sub": "user_1deJLArSTiWiF1YdsEWysnhJLLY",
 "user_id": "user_abcdef123456789",
 "avatar": "https://example.com/avatar.jpg",
 "full_name": "Doe Maria",

wtf are jwks

WTF Are JWKS

The signature depends on a secret key. In the example above that's the string "neonauthorizeiscool". In production, you use asymmetric cryptography: your auth provider signs with a private key and publishes the corresponding public key so anyone can verify tokens without ever accessing the private key.

Those public keys live at a JWKS endpoint — usually /.well-known/jwks.json:

json 
{
          "keys": [
            {
              "kid": "key-identifier-2023",  // Key ID - matches the kid in JWT header
              "kty": "RSA",                  // Key type - usually RSA or EC
              "alg": "RS256",                // Algorithm - like RS256 for RSA SHA-256
              "use": "sig",                  // Usage - 'sig' for signing
              "n": "long-base64-number...",  // RSA public key modulus
              "e": "AQAB"                    // RSA public exponent
            }
          ]
        }

When your app receives a JWT, the verification dance goes like this: read the kid (key ID) from the JWT header, fetch the JWKS from your auth provider, find the matching public key, use it to verify the signature. If it passes, the claims are trustworthy.

  • Key rotation — providers swap keys without breaking existing tokens
  • Multiple environments — different keys for staging vs. production
  • Zero-trust — every single request is independently verified

authorization flow

How JWTs Work in Authorization

The flow splits into two phases. First, authentication: the user logs in through your auth provider, which verifies credentials and generates a JWT. That JWT gets stored in your app — usually in memory or a secure cookie.

Second, authorization: your app sends a request to your backend or database with the JWT in the Authorization header. The receiving service verifies the JWT using the JWKS endpoint, then uses the claims to make authorization decisions.

In a multi-tenant app, the flow looks like this:

  • Neon extracts tenant_id from the JWT claims
  • The RLS policy checks if that matches the row's tenant_id
  • The user only sees data from their own organization
💡 Tip

Authorization enforced at the database level means no separate permission tables and no application-layer gate to accidentally bypass. Each request is independently verified. That's the zero-trust model JWTs make practical.

"Enforced at the database level" means an accidental data leak now has to defeat the cryptographic signature AND the RLS policy. Sleep better.

signing vs encrypting

Signing vs. Encrypting

This distinction trips up more people than it should. Signing and encryption are different operations with different guarantees — and confusing them leads to real security mistakes.

❌ What signing does NOT give you
Privacy — the payload is publicly readable
Secret data storage — never put PII or credentials here
Protection if the token is intercepted
✅ What signing DOES give you
Authenticity — proves the token hasn't been tampered with
Trust — verifies which provider issued the token
Stateless verification — no database lookup needed

The JWT in your Authorization header right now is base64-encoded. Decode it with any online decoder and you can read every claim. "base64" is not encryption — it's just a different way of spelling the same string.

⚠️ Warning

Never put sensitive data in a JWT payload — SSNs, payment info, plaintext credentials. Store a non-sensitive identifier (user_id, sub) and look up sensitive fields from your database when you need them. If you genuinely need encrypted JWTs, that's JWE (JSON Web Encryption) — a separate spec entirely.

jwt ftw

JWT FTW

Three base64-encoded segments solving distributed auth at scale. Your auth provider handles key generation and JWKS publishing. Your database uses the claims for row-level security. You write business logic instead of reinventing sessions for the third time.

"Think of a JWT as a signed security badge — it proves who you are and what you're allowed to do, but don't write anything private on the back."

  • JWTs are self-contained — all claims travel with the token, no DB lookup to verify
  • They're signed, not encrypted — readable by anyone, trusted because of the signature
  • Your auth provider handles the hard stuff — key management, rotation, JWKS publishing
  • Use claims for authorization decisions — never for storing sensitive data
