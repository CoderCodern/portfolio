Skills: The Passive Knowledge Layer That Makes Claude Actually Good at Your Job

May 2026 14 min read Skills · Four Patterns · Global vs Local · Real templates

After two weeks of Claude Code, I kept running into the same friction: Claude was smart, but it didn't know my workflows. Not the TDD process my team follows, not our REST API conventions, not how we handle errors. Every session I re-explained the same things. Skills are the fix — but before I understood what they actually are, I had completely the wrong mental model. Let me fix that first.

The Mental Model Most People Get Wrong

Skills are not commands. They're not agents. They're not "smart prompts." Skills are passive knowledge modules. Claude Code loads them based on context and references them when relevant — automatically, without you invoking anything.

Here's the full ecosystem and where Skills sit within it:

Component
What it is
When it activates
Skill
Passive knowledge module
Context-based — automatic
Agent
Specialized subassistant
Explicit delegation via Task tool
Command
User-triggered action
You type /command-name
Hook
Automation script
Event-triggered (tool use, session end)
Rule
Always-on guidelines
Every message, every session
⚡ The key implication
A skill does not execute anything. You invoke agents to do work. Agents read skills to know how to do it well. If you find yourself writing a skill that "runs" something — you probably want a command or a script-backed skill with a companion executable.
where it lives

Global vs Local — Where Your Skill Lives

Before building anything, decide where it belongs. This determines who sees it, when it loads, and whether it ships with your project.

Full folder map 
# GLOBAL — applies to all your projects
~/.claude/
└── skills/
    ├── my-coding-style/     ← your personal workflow skill
    │   └── SKILL.md
    ├── my-git-style/        ← cross-project git conventions
    │   └── SKILL.md
    └── learned/             ← auto-generated by Claude, don't edit
        └── session-log.md

# LOCAL — specific to one project (committed to git)
your-project/
└── .claude/
    └── skills/
        ├── api-design/      ← team-shared REST conventions
        │   └── SKILL.md
        ├── tdd-workflow/    ← team-shared process enforcement
        │   └── SKILL.md
        └── brand-voice/     ← team-shared content guidelines
            ├── SKILL.md
            └── references/
                └── voice-profile-schema.md
🌍
~/.claude/skills/my-skill/global
Available in all your projects. Never committed to git. For personal workflows and your coding philosophy.
👥
.claude/skills/my-skill/project
This project only. Committed to git and shared with your team. For project conventions, domain knowledge, team processes.
🤖
~/.claude/skills/learned/auto
Auto-generated by Claude based on session patterns. Don't edit manually — let Claude manage this.
💡 Rule of thumb
If it's about how you work → global skill (~/.claude/skills/). If it's about how this codebase works → project skill (.claude/skills/).
anatomy

Anatomy of a Skill

Every skill is a directory with at least one required file:

Skill directory structure 
.claude/skills/my-skill/
├── SKILL.md          ← required, must be non-empty
├── config.json       ← optional — configurable behavior
├── scripts/          ← optional — companion executables
│   └── run.js
└── references/       ← optional — sub-documents for heavy schemas
    └── schema.md

The Frontmatter

SKILL.md frontmatter 
---
name: api-design          # must match directory name exactly
description: REST and GraphQL API conventions, HTTP status codes, pagination
              # ↑ inline string ONLY — never use | or |- literal blocks
origin: user              # user | community | ECC
---

The Four Required Sections

SKILL.md — section order 
## When to Activate    ← most important — runtime uses this for auto-discovery

## Core Reference       ← the actual knowledge: tables, rules, conventions

## Code Examples        ← copy-pasteable, not pseudocode

## Anti-Patterns        ← what NOT to do, with concrete examples

Length target: 200–500 lines. Hard cap at 800. A skill over 800 lines is a skill trying to be two skills. Split it.

activation

The "When to Activate" Section Is Load-Bearing

This is not just documentation. It's the primary signal the runtime uses to decide whether to load this skill into context at all. A vague section means the skill fires late, inconsistently, or never. Write at least 4 specific, concrete scenarios.

❌ Bad — too vague
## When to Activate - When working on APIs.
✅ Good — specific triggers
## When to Activate - Designing new REST or GraphQL endpoints - Reviewing an API contract for consistency - Adding pagination to a collection endpoint - Writing OpenAPI documentation - Deciding between REST and GraphQL - Implementing error response schemas
four patterns

The Four Design Patterns

After studying the ECC project (Everything Claude Code) — 200+ skills shipped to production — real skills fall into exactly four patterns. Knowing which one to use before you start prevents full rewrites.

A
Pure Reference
Just a SKILL.md. Dense, structured, heavy on tables and code snippets. No scripts, no sub-docs.
API conventions · Language idioms · Design rules
B
Script-Backed
SKILL.md describes the workflow, companion scripts execute it. The skill orchestrates; the script does the work.
Session analysis · File generation · Data fetching
C
Workflow
Prescriptive, not just reference. Defines sequential steps Claude must follow — a process to enforce.
TDD enforcement · PR review process · Deploy checklist
D
Reference + Sub-docs
Lean SKILL.md that delegates heavy structural details to a references/ subdirectory. Main file stays scannable.
Brand voice · Schemas · Reusable artifact producers

Pattern A — Pure Reference (the most common starting point)

Pattern A — folder structure 
.claude/skills/api-design/
└── SKILL.md              ← 524 lines, dense tables and code snippets
                              no scripts, no sub-docs
                              stable domain, just needs reference mid-task
.claude/skills/api-design/SKILL.md 
---
name: api-design
description: REST API design conventions, HTTP status codes, pagination, error schemas
origin: user
---

## When to Activate
- Designing new REST or GraphQL API endpoints
- Reviewing API contracts for consistency
- Adding pagination or filtering to collections
- Writing OpenAPI documentation
- Defining error response shapes

## Core Reference

### URL conventions
- Resources are plural nouns: /users, /invoices — not /getUser
- Nested resources for ownership: /users/{id}/invoices
- Actions that don't map to CRUD: /invoices/{id}/send

### HTTP status codes
| Code | Use case                                   |
|------|--------------------------------------------|
| 200  | Successful GET, PATCH                      |
| 201  | Successful POST (resource created)         |
| 204  | Successful DELETE (no body)                |
| 400  | Malformed request / validation failure     |
| 401  | Missing or invalid auth token              |
| 403  | Valid token, insufficient permissions      |
| 404  | Resource not found                         |
| 409  | Conflict (duplicate, state mismatch)       |
| 422  | Business logic rejection                   |
| 500  | Internal error — never leak details   |

## Code Examples
// ✅ Standard error shape — use everywhere
{
  "error": {
    "code": "INVOICE_ALREADY_SENT",
    "message": "This invoice has already been sent.",
    "field": "status"
  }
}

## Anti-Patterns
- ❌ Verbs in URLs: /getInvoice, /createUser
- ❌ Returning 200 for errors with success: false in body
- ❌ Using 500 for client mistakes — that's a 4xx
- ❌ Different error shapes per endpoint

Pattern B — Script-Backed (workflow + execution)

Key design decision from ECC: use a Stop hook (fires once at session end), not a UserPromptSubmit hook (fires every message). One execution vs. dozens — the overhead difference is enormous.

Pattern B — folder structure 
.claude/skills/continuous-learning/
├── SKILL.md              ← defines the workflow Claude orchestrates
├── config.json           ← configurable thresholds (duration, output path)
└── evaluate-session.sh   ← companion script that does the actual work
                              triggered by Stop hook — once at session end
.claude/skills/continuous-learning/SKILL.md 
---
name: continuous-learning
description: Evaluate each coding session and extract lessons for future improvement
origin: user
---

## When to Activate
- At the end of any coding session
- When a task takes significantly longer than expected
- After fixing a bug that required multiple correction cycles
- When a pattern appears that should be remembered

## Core Reference
This skill runs via a Stop hook — once at session end, not per-message.

### What to evaluate
1. Decisions made and why
2. Mistakes and how they were corrected
3. Patterns that worked well
4. Patterns to avoid next time

### Output format
Append to ~/.claude/skills/learned/session-log.md:
- Date + project
- Key decisions
- Lessons extracted
- Rules to add to CLAUDE.md (if any)
.claude/skills/continuous-learning/config.json 
{
  "min_session_duration_minutes": 10,
  "output_path": "~/.claude/skills/learned/session-log.md",
  "max_lessons_per_session": 5
}

Pattern C — Workflow (process enforcement)

Pattern C — folder structure 
.claude/skills/tdd-workflow/
└── SKILL.md              ← 514 lines, zero companion files
                              prescriptive steps, not just reference
                              enforces process, not just informs it
.claude/skills/tdd-workflow/SKILL.md 
---
name: tdd-workflow
description: Test-driven development workflow with git checkpoints and coverage gates
origin: user
---

## When to Activate
- Implementing any new feature
- Fixing a bug (write regression test first)
- Refactoring existing code
- Adding a new API endpoint

## The Workflow

### Step 1 — Write the failing test
Write a test describing the desired behavior. Run it. Confirm it fails (RED).
Never skip — a test that doesn't fail first isn't a test.

### Step 2 — Implement the minimum
Write the minimum code to make the test pass. No extra logic. GREEN only.

### Step 3 — Git checkpoint
git add -p          # stage intentionally
git commit -m "feat: [description] (green)"

### Step 4 — Refactor
Clean up. Remove duplication. Run tests after every change.
Never refactor on a red test.

### Step 5 — Verify coverage
pnpm test:coverage
# Gate: no new lines below 80% branch coverage

## Mocking patterns (this project)
- Supabase: use createMockSupabaseClient() from src/test/mocks/supabase.ts
- Redis: use ioredis-mock — never mock Redis manually
- OpenAI: use nock to intercept HTTP — not jest.mock

## Anti-Patterns
- ❌ Writing implementation before the test
- ❌ Committing on a red test
- ❌ Skipping the refactor step

Pattern D — Reference + Sub-Documents

Pattern D — folder structure 
.claude/skills/brand-voice/
├── SKILL.md                      ← 98 lines, stays scannable
└── references/
    └── voice-profile-schema.md   ← heavy schema, loaded on demand
                                      consumed by downstream skills
.claude/skills/brand-voice/SKILL.md (98 lines — stays scannable) 
---
name: brand-voice
description: Generate consistent brand voice profiles for content and documentation
origin: user
---

## When to Activate
- Writing customer-facing documentation
- Drafting marketing copy or product descriptions
- Reviewing content for tone consistency

## Core Reference
Produce a VOICE PROFILE block using the schema in
references/voice-profile-schema.md.

The three voice dimensions:
- Clarity   — plain language, no undefined jargon
- Warmth    — human, not corporate; confident, not boastful
- Precision — specific claims, not vague reassurances

## Anti-Patterns
- ❌ Generic tone ("professional and friendly") without signals
- ❌ Passive voice in action-oriented contexts
- ❌ Different voice in docs vs in-product copy
anti-patterns

Anti-Patterns Worth Memorizing

From the ECC project's contributing guide and skill validation policy — the failures that appear most often in skill reviews:

Anti-PatternWhy it fails
Scope too broadOne skill = one domain. "Python, Django, and Flask" is three skills.
No code examplesTheory without practice isn't actionable when Claude is mid-task.
Vague "When to Activate"Auto-activation won't fire reliably. Needs 4+ specific scenarios.
Long prose sectionsHard to scan mid-task. Use tables, bullets, and headers.
description as literal block (|)Breaks flat-table renderers downstream. Always inline string.
name ≠ directoryValidator fails immediately. Must match exactly.
Script using UserPromptSubmit hookRuns every message. Massive overhead. Use Stop hook instead.
Over 800 linesSplit it. A skill that long is two skills fighting for space.
⚠️ On porting skills from other tools
Copy the underlying idea, workflow, or structure — not the identity. A skill that requires knowing the upstream repo to understand its purpose is a skill that will confuse future-you at 11pm. Rename it. Reshape it. Make it native to your project.
ship it

The Checklist Before You Ship

  • Focused on exactly one domain — not too broad
  • "When to Activate" has 4+ specific, concrete scenarios
  • At least one copy-pasteable code example (not pseudocode)
  • At least one Anti-Patterns section with concrete examples
  • Under 500 lines (800 hard cap — split if over)
  • Frontmatter: name matches directory, description is inline string
  • No sensitive data — no tokens, passwords, or absolute local paths
  • If script-backed: uses Stop hook, not UserPromptSubmit
  • If porting from another tool: renamed and reshaped to be native
  • Tested: trigger a session where it should activate, verify it does
the bigger picture

How Skills Fit the Full System

Skills, CLAUDE.md, and SOUL.md aren't competing — they're layered. Each handles a different kind of context:

SOUL.md
How Claude communicates — tone, style, response defaults
CLAUDE.md
What Claude knows about you and your project — permanent briefing
Skills
Domain knowledge Claude draws from mid-task — auto-loaded when context matches
Commands
Explicit workflows you trigger yourself — /review-pr, /deploy, /document
Hooks
Automation that fires on events — linting, secret detection, session logging

"Write skills you'd want to use yourself. If you wouldn't reference it mid-task because it's too vague, too long, or too broad — neither will Claude."
